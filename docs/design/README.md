# 画面の設計 — 調査を踏まえて作った記録

**ここにある調査と設計の文書は、Claude の学習済みの知識に基づく。各ストアの実物のページは読んでいない**。数値は記憶によるもので、実物と異なる可能性がある。各文書では項目ごとに確信度を［高］［中］［低］で示し、公式ガイドラインの公開値（事実）と、ストアの画面についての記憶（推測）を区別している。

出発点は、最初の試作（v1）を見た依頼者の言葉である。
「App Store とか Google Play Store とかって、こんなしょぼいデザインじゃない」「世界中にあるこういったプラットフォームの類のデザイン、UI、UX の英知をまずは調査し、それを踏まえた上で作り込んでください」。

## 参考にしたストアと、取り入れなかったもの

主に参考にしたのは、iOS の App Store と Mac App Store である（Today カード、3 行の横並びの一覧、大きな角丸、アイコン中心の構成、アクセント色は青 1 色）。取り入れなかったのは、星とレビュー（要件 R6）、純黒のダークモード、SF 書体とガラス風の質感である。ほかのストアから取り入れたのは、企業向けのストアにある、「ストアによる確認」にあたるチェック行（Slack App Directory・Atlassian Marketplace の、信頼を示す要素の型）、区分（オフィシャル／インディーズ）のタイル、公開画面の「審査を申請」のスイッチである。

## 画面を描画して確かめる

```
pip install playwright
python -m playwright install chromium
python docs/design/shoot.py store.html shots
```

`shots/` に PNG 72 枚と `errors.txt`（JS のエラーと横スクロールの有無）が出力される。別の場所にある Chromium を使うときは、環境変数 `CHROMIUM_PATH` にその実行ファイルのパスを設定する。インターネットに接続できない環境では、Google Fonts の読み込みに失敗したことが `errors.txt` に記録されるが、画面は OS の日本語フォントで描画される。

## 検証（v2.1 → v2.2）

must 33 件を 5 つの視点（PC の見た目／詳細画面と文言／スマホとダークモード／コード／操作）に割り振り、1 件ずつ見直した。操作の視点では、担当の 6 件に加えて v2.1 の変更点 7 種を Playwright で実際に操作して確かめたので、確かめた数は 40 になる。表の語は、いまの画面の語に置き換えてある。

| 結果 | 件数 | 何が残っていたか |
|---|---|---|
| 直っていた | 30 | — |
| 一部残っていた | 10 | 詳細画面の主ボタン（PC 幅）が、入手や申し込みの後も切り替わらない（`refreshPills` が `.row-act` の中しか見ておらず、ヘッダーの主ボタンはその外にあった）。スマホでのピルの縮小が、後に書かれた素の `.pill` の指定に上書きされていた。カテゴリーのタイルを 4 列にすると、幅 940〜1023・1168〜1263 で名前が切れていた。「もっと見る」と有償の単位の欄が 44px に満たない。固定バーの単位（「1人・1月」など）の文字が 11px・太さ 400 だった。ダークモードでスイッチのノブに影が残る。スマホの固定バーに「インディーズ」が出て、3 か所目の表示になる |
| 新たに見つかった must | 6（候補は 7 件。反証を担当した 2 人が 1 件を should に下げた） | 上と同じ原因の主ボタンの件が、3 つの視点から重複して挙がった。ほかに、ファイルをストアで保管していない成果物で、「入手できない場合」の案内に「共有フォルダにもある」と表示される、スマホで縮んだヘッダーと固定バーに主ボタンが 2 つ出る、審査の表の行に見出し用の `.ph` が当たって空行が入る |

v2.2 で 16 件すべてを直し、Playwright で数値を測って確かめた。要点は次のとおり。PC 幅で「入手」を押すと主ボタンが「開く」に、「申し込む」を押すと「申し込み中」に変わり、もう一度クリックしてもシートは開かない。状態ピルの文字のコントラストは、ライト 7:1 以上・ダーク 7:1 以上（`color-mix` で `--label` 72%）。幅 400 で見える主ボタンは、固定バーの 1 つだけ。カテゴリーのタイルは、940〜1280 のどの幅でも名前が切れない（4 列になるのは 1264 以上）。審査の表の行の高さは 83px から 59px に縮んだ。

must から外した 1 件（「特集」の大カードの面が、ただのグラデーションに見える）は、仕様の 4 章 D の記述どおりであり、受け入れ基準にも無いため should として扱った。次に絵を足すなら、ここが候補になる。

## v2.3 で直したこと

**文言**。3 人がそれぞれ別の方針で全文を書き直した（App Store の日本語 UI に寄せる／Microsoft 365 の業務用語に寄せる／平易な日本語に寄せる）。それを 1 人が 1 本に統合し、別の 1 人が漏れや直し残しをチェックした。決めた原則は次のとおり。

- 比喩の語を使わない。店→ストア、棚→カテゴリー、入口→区分、作り手→作成者、係→審査担当者、画面の顔→デザイン
- 依頼者の語（成果物・オフィシャル・インディーズ・審査・審査済み／未審査・ツール・素材・カテゴリー・無償／有償・公開）を最優先し、足りないところは、業務システムと App Store で定着している語（作成者・申請・承認・差し戻し・対応環境・バージョン・サブタイトル）で補う
- 1 つの対象には 1 つの語を当て、画面ごとに言い換えない
- ボタンの文言は動詞で終える（公開する・審査を申請する・承認する・差し戻す・申し込む）。「入手」「開く」「キャンセル」「閉じる」は定型として残す
- 見出しと欄名は名詞句にする。本文とヒントは敬体にする。空の状態は 2 行で示す（1 行目は事実、2 行目は次にできること）
- 単位「1人・1月」は「一月（いちがつ）」とも読めるので、「1人あたり月額」「1部門あたり月額」「1人分の買い切り」にした

v2.3 で置き換えた語の対応（主なもの）:

| 以前の語 | いまの画面の語 |
|---|---|
| 店 | ストア |
| 棚 | カテゴリー |
| 入口 | 区分 |
| 作り手 | 作成者 |
| 作り手の申告 | 作成者からの情報 |
| 店が確かめたこと | ストアによる確認 |
| 審査係 | 審査担当者（その画面とナビは「審査待ち」） |
| 頼む／認める／戻す | 申請する／承認する／差し戻す |
| 直して、もう一度頼む | 再申請する |
| 使う環境 | 対応環境 |
| 版 | バージョン |
| 入手のようす | 入手の傾向 |
| できること（作成者からの情報の見出し） | 特徴 |
| 最近よく入手 | 人気上昇中 |
| もとにしたもの | 参考にした成果物 |
| 無料／有料・値段 | 無償／有償・金額 |
| ひとこと／何ができるか／くわしく | サブタイトル／概要／詳しい説明 |
| 画面の顔 | デザイン |

**レイアウト**。描画した画面を測り、原因を特定してから直した。数値は PC 幅 1280 でのもの。

- 詳細画面の情報バー（価格・更新・対応環境・入手の傾向）: 高さ 64 に固定した枠に 61 の中身が入り、文字と上下の線の間が 3px しかなかった。縦線が上下の線まで届いて升目のように見え、欄ごとに縦線までの間隔もばらつき、補足の無い欄だけが 9px 下がっていた。バーをヘッダーと同じ幅 932 に収め、上下に 16 の余白を取り（高さ 97）、欄を等分して中央にそろえ、縦線が上下の線に触れない形にした
- 詳細画面のヘッダー: 空の 2 行目の上に余白が入り、入手ボタンがアイコンより 20px 下にずれていた。ボタンの下端をアイコンの下端にそろえた
- 見本のパネル: 縦長（240×320）だったため、横長の文書やブラウザの見本まで縦長の枠に入り、ファイル名が 2 行に分かれていた。横長の 384×240（16:10）にし、中の紙・ブラウザ枠・フォルダの寸法も決め直した。ファイル名はどの幅でも 1 行に収まる
- オフィシャル／インディーズのページの大カードの面（12:5）が、Today カードより背が高かった。比率を 3:1 にして Today より低くし、中のアイコンを 96 から 120 に大きくした
- ホームの Today カードで、文字の左端と下のバーのアイコンの左端が 4px ずれていた。詳細画面の各節で、見出しと中身の間隔をホームと同じ 16 にした
- 描画を見て追加した修正: 情報欄の「バージョン」の行から価格を外した（価格は情報バーとボタンに表示されている）。説明文やタイルの文が語の途中で改行されていたので、`word-break: auto-phrase` を指定した

`spec.md` に書いてあった寸法（情報バー 64、見本のパネル 240×320、大カード 16:9）も、上と同じ数値に直した。

## 検証（v2.3）

文言・レイアウト・操作の 3 つの視点の検証担当が、描画した画面と Playwright で確かめた。指摘は must 3・should 13・nice 15。

| must | 直し方 |
|---|---|
| 詳細画面の「できること」の下に、できることではない句（「マクロなし」「A3」など）が並んでいた | 見出しを「特徴」に変えた |
| 幅 1024〜1105 で、5 欄あるオフィシャルの情報バーの最後の欄が、右端で切れていた（情報バーのスクロールバーは非表示にしてある） | 欄の左右の余白を、1024 以上では 12、1024〜1167 では 8 にした |
| 検索で区分を絞り込んで 0 件になると、区分の切り替えまで消え、ほかの区分に結果があっても「一致なし」と表示された | 切り替えを残し、「すべての区分では 3件見つかりました」と表示するようにした |

should と nice から採用した主なもの: 「入手状況」→「入手の傾向」（「入手したかどうか」と読めるため）、インディーズの注意書きの「他部門での動作」→「ほかの部門で使えるか」（素材は動作するものではないため）、有償の説明を 3 か所で同じ文にそろえる、申し込みのシートに提供部署（成果物の「収入の計上部署」）を表示する、スマホの固定バーでも申し込んだ後は「提供部署の承認待ち」と表示する、必須項目だけで公開したときは空の見本と説明の節を出さない、審査のコメント欄を承認のときにも使う欄として説明する、URL を手で入力しても、審査待ちに入っていない成果物は審査の画面に出さない、自分の有償の成果物には申し込めないようにする、未入力の項目があると最初の欄に移動する、特集ページの見出しを語の区切りで改行する、1024〜1263 で Today カードのアイコンを文と重ねない。

採用しなかったもの: 詳細画面の主ボタンを、説明ボックスの有無にかかわらず見出しの段にそろえる案（依頼者が指摘していない見た目の変更になるため）。

直した後に確かめたこと: 34 件 × 幅 1024・1060・1105・1167・1280 で、情報バーのはみ出しは 0。Today カードの文とアイコンの重なりは、幅 600〜1440 で 0（検証担当の案どおり 1167 までにすると 1168〜1224 で重なりが残ったので、1263 まで広げた）。検索の 0 件、スマホでの申し込み（再読み込みの後も状態が残る）、必須項目だけの公開、審査の URL の手入力は、Playwright で実際に操作して確かめた。72 枚の描画で JS のエラーは 0（Google Fonts の読み込みの失敗だけが出る。これは作業環境の都合による）。
