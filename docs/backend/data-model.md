# データモデル

成果物のストアのバックエンドで持つデータの形式を、1 か所にまとめる。
構成と処理の流れは [architecture.md](architecture.md)、構築の手順は [implementation-guide.md](implementation-guide.md) にある。

この文書にある仕様や上限の記述は、学習データにもとづく記憶による。
**［要確認］** が付いた箇所は、導入先で確かめてから使う。確かめる方法は、同じ行か [implementation-guide.md の「導入先で確かめること」](implementation-guide.md#導入先で確かめること)（T01〜T25）に書いてある。

## 1. 共通の決まり

どの置き場に移ってもそのまま持っていけるように、次の決まりを守る。

| 決まり | 理由 |
|---|---|
| **1 件を 1 レコードにする。** 成果物 1 件は、リストでは 1 行、JSON では 1 オブジェクトになる | 置き場（共有フォルダ、SharePoint、Git、データベース）が変わっても、行と件が 1 対 1 で対応する |
| **id で指す。** 置き場が振る番号（SharePoint の行の ID など）は、書き出すデータに入れない | 置き場を移ると、その番号は引き継がれない。id は移っても変わらない |
| **参照列（ルックアップ）を使わない。** 成果物や部署は、id やコードの文字列で指す | 移すときに参照が切れない。また、1 つのビューで使える参照列の数には上限がある（12 と記憶している［要確認: 参照列は使わないので試さなくてよい。使うことになったら SharePoint 管理者に確認する］） |
| **選択肢の値は、JSON の値（半角英字）で持つ。** 画面で日本語に置き換えて表示する | 書き出すときに変換せずに済む。画面の表記を変えても、データは変わらない |
| **人は Entra ID のオブジェクト ID で指す。** 名前と部署は、その時点の値を写して持つ | 名前やメールアドレスは変わることがある。オブジェクト ID は変わらない |
| **年月は文字列（`YYYY-MM`）で持つ。** 付け替えの対象月や計上月度に使う | 日付の列は、タイムゾーンの扱いで 1 日ずれることがある。月の境目でずれると、付け替えの月が変わってしまう |
| **日付は日本時間の日付（`YYYY-MM-DD`）で持つ。** 時刻まで必要なものは日時の列にし、書き出すときは `+09:00` を付ける | 試作の `updated` と同じ形式。月末の締めは日本時間で区切る |
| **金額は円の整数で持つ。** 打ち消しは負の数にする | 端数や通貨の換算を持ち込まないため |
| **行を消さない。** 取り下げや取り消しは、状態を変えて残す（例外は 11 章） | 系譜と付け替えの記録が途切れないようにするため |

列の名前は **半角英字の内部名** で作り、あとで表示名を日本語に変える。
日本語の名前で列を作ると、内部名が読めない符号の並びになり、フローの式が書きにくくなるためである［要確認: 試験用の列を英字で作ってから表示名を変え、列の設定画面の URL の末尾が英字のまま残るかを確かめる］。
リストとライブラリも、英字の名前で作ってから表示名を変える（URL が英字のまま残る）。

SharePoint にすでにある列と同じ名前で作ると、内部名に `0` が付くか、作成できない。`Order`（どのリストにも同じ名前の隠し列がある）と `Version`（バージョン履歴の列の表示名）は、既存の列と名前が重なると記憶している［要確認: 試験用のリストで `Order`・`Version`・`Type`・`State`・`Count` の列を作り、列の設定画面の URL にある `Field=` の値が、作った名前と同じかを確かめる］。そこでこの文書では、並び順の列を `SortOrder`、バージョン番号の列を `ItemVersion` という名前で作る。JSON の項目名（`version`）は変えない。

**`Title` の扱い:** SharePoint のリストの `Title` 列は、既定で必須になっている。この文書では必須をリストの設定で付けない（3 章の表の下）ので、`Title` の必須も列の設定で外す。ただし、利用者が作る行では、画面が `Title` に次の値を入れ、空の行は作らない。入手の記録は `ItemId`、申し込みは `ClientToken`（後でフローが申し込み ID に書き換える）、作成者の数字は `maker` を入れる。**一意の制約を付けた列を空にした行を、2 行作れるか** は、記憶があいまいである［要確認: 試験用のリストで、一意の制約を付けた列を空のまま 2 行作れるかを確かめる］。作れなければ、取り込んだ成果物の `SourceRequestId` に `-1` から順に負の数を入れる。

- 日付の項目を「1 行テキスト」にするのは、1 章に書いた日付の列のずれを避けるためである。`YYYY-MM-DD` の形式なら、文字列の順で並べ替えても正しく並ぶ。

- リストの「バージョン管理の設定」でバージョン履歴を有効にする。これで、誰がいつ何を変えたかが残る［要確認: 保持するバージョン数の既定値を、リストの設定で確かめる］。
- インデックスは最初から付けておく。表示しきい値（5,000 件［要確認: T15］）を超えてからでは、付けられないことがある［要確認: T15］。インデックスは 1 リストにつき 20 までと記憶している［要確認: T15 の試験用のリストで、インデックス付きの列の画面に上限が表示されるかを確かめる］。この表でインデックスを付ける列は 8 つ（`ItemId`・`Tier`・`Shelf`・`MakerId`・`Updated`・`ReviewStatus`・`State`・`SourceRequestId`）。

### 3.1 ファイル（`ItemFiles` と `PaidFiles`）

- 置き場所は `/<id>/<ファイル名>`。**区分（オフィシャル・インディーズ）をパスに入れない。** そうすれば、昇格してもファイルは移動せず、リンクも切れない。
- 試作の「入手できない場合」のシートは、区分を含むパス（`\\share\store\<tier>\<id>\`）を表示している。このパスは昇格すると変わるので、画面を直すときに `/<id>/` に合わせる（architecture.md 12 章）。
- 列は `ItemId`（1 行テキスト・インデックス）だけ。
- バージョン履歴を有効にし、バージョンを上げたときに前のファイルが残るようにする。
- 有償の成果物のファイルは `PaidFiles` に置く。読めるのはストア管理者と審査担当者（審査に必要なため）、書けるのは運用アカウントだけにする（ライブラリ単位で権限の継承を中止する。2 章の表と architecture.md の権限の表に同じ）。

## 5. カテゴリー（`Categories`）— `categories.json`

`categories.json` の入れ子の構造を、`Type` 列で種類を分けた 1 つの表にまとめる。

| 列 | 型 | tier の行 | kind の行 | shelf の行 | signal の行 |
|---|---|---|---|---|---|
| `Type` | 選択肢 `tier`・`kind`・`shelf`・`signal` | `tier` | `kind` | `shelf` | `signal` |
| `CatId` | 1 行テキスト | `tiers[].id` | `kinds[].id` | `kinds[].shelves[].id` | `signals[].id` |
| `Title` | 1 行テキスト | `tiers[].name` | `kinds[].name` | `shelves[].name` | `signals[].name` |
| `Sub` | 1 行テキスト | `tiers[].sub` | — | — | `signals[].why` |
| `SubShort` | 1 行テキスト | — | — | — | `signals[].sub` |
| `Parent` | 1 行テキスト | — | — | 属する大カテゴリーの id | — |
| `SortOrder` | 数値 | 並び順 | 並び順 | 大カテゴリーの中での並び順 | 並び順 |
| `Hue` | 数値 | — | — | 色相（**新**） | — |
| `Active` | 選択肢 `yes`・`no` | | | | |

- 中カテゴリーの色相は、試作では雛形のコード（`const HUE`）に書かれている。これをデータに移し、画面はこの列から読む。
- **id は変えない**（成果物が id で指している）。表示名はいつ変えてもよい。
- 行を消す代わりに、`Active` を `no` にする。`no` にした中カテゴリーに成果物が残っていれば、書き出しのフローが知らせる。

## 6. 受付（`Requests`）— 書き込み操作の窓口

画面からの書き込み操作は、どれも「受付に 1 行書く → フローが確かめて反映する」という流れになる（architecture.md 5 章）。
例外は、入手（`Acquisitions` に直接書く）と申し込み（`Applications` に直接書く）の 2 つである。

| 列 | 型 | インデックス | 備考 |
|---|---|---|---|
| `Title` | 1 行テキスト | | 件名。公開の場合は成果物の名前 |
| `RequestType` | 選択肢（下の表） | ○ | |
| `TargetId` | 1 行テキスト | ○ | 操作の対象。成果物の id、申し込み ID、記録キー、締め ID、締める月（`YYYY-MM`）のいずれか |

| `PriceType`・`PriceAmount`・`PriceUnit`・`RevenueDeptCode` | 成果物と同じ型 | | 有償の場合の入力内容 |
| `ProviderApprovers` | ユーザー（複数） | | 申し込みを承認する人（任意。収入の部署の人に限る） |
| `Maintainers` | ユーザー（複数） | | 保守担当者の指名（公開と `maintainers` で使う） |

### 7.2 入手の記録（`Acquisitions`）と集計

**入手の記録**（自分の行だけ読める）

| 列 | 型 | 備考 |
|---|---|---|
| `ItemId` | 1 行テキスト・インデックス | |

| 登録者・`Created` | SharePoint が付ける・インデックス | 誰がいつ入手したか |

- 無償の成果物で「入手」を押すと、画面がその人として 1 行書く。同じ成果物については 1 人 1 行とする（画面が自分の行を確かめ、重複して書かない）。
- 利用者は行を作れるが、編集はできない（権限レベル「追加と閲覧だけ」）。ただし、リストの画面から行を追加することはできるので、集計では行の数ではなく、登録者と成果物の組み合わせで数える（architecture.md 6.13）。

- 生の記録の行は、設定 `RawKeepDays` の日数（既定 90 日）が過ぎたら消す。消えると、その人の画面の「入手済み」は「入手」に戻る（architecture.md 6.6）。

### 7.3 申し込み（`Applications`）

利用者が画面から 1 行作り、自分の行だけを読める。**利用者は行を作れるが、編集も削除もできない。** 残りの列はフローが書く。このリストには、サイトに作った権限レベル「追加と閲覧だけ」を全員に与える（内容は architecture.md 7.2）［要確認: 試験用の利用者で次の 2 点を確かめる。Power Apps から 1 行作れること。リストの画面と REST のどちらからも、自分の行の `State` を直せないこと］。

**利用者が作ったままの行は信用しない。** 利用者は行を作るときに、どの列にも値を入れられる（`State` を `active` にした行を作ることもできる）。そのため、承認・付け替え・締めのフローでは、最終更新者（`Editor`）が運用アカウントになっている行だけを使う。フローが一度でも書き込んだ行は最終更新者が運用アカウントになり、利用者はそれ以降、編集できない。最終更新者がまだ利用者のままの行は「未処理」として扱う（architecture.md 6.16）［要確認: T08 の試験で、フローが更新した行の「更新者」が運用アカウントになるかを確かめる。最終更新者を偽装できないかは T09 で確かめる］。

### 7.6 部署コードの一覧（`Depts`）

| 列 | 型 | 備考 |
|---|---|---|
| `Title` | 1 行テキスト・一意・インデックス | 部署のコード。経理のコードをそのまま使う |
| `DeptName` | 1 行テキスト | 部署の名前 |
| `DirectoryDept` | 1 行テキスト | 名簿（Entra ID）の部署欄の値。申し込んだ人の部署とコードを対応づける。空でもよい |
| `ValidFrom`・`ValidTo` | 1 行テキスト（`YYYY-MM-DD`） | 有効期間。廃止したら `ValidTo` に日付を入れる |
| `CostApprovers` | ユーザー（複数） | 費用側の承認と、ほかの部署がこのコードを収入の部署に指定するときの承認を行う人（任意） |
| `Active` | 選択肢 `yes`・`no` | 画面の選択肢に出すか |

- 全員が読める（画面に選択肢を出すため）。
- 内容は、経理の部署の一覧から取り込む。経理担当が、部署の取り込みのライブラリ（`DeptImport`）に CSV を置く。このライブラリには経理担当とストア管理者が書き込めるようにし、経理への引き渡しのライブラリとは分ける。CSV が置かれたら、ストア管理者が取り込みのフローを手動で実行する（implementation-guide.md 段階 7）。
- CSV は UTF-8 で受け取る。フローの標準の操作には、Shift_JIS から変換する操作が無いと記憶している［要確認: Shift_JIS の CSV を試しに「ファイル コンテンツの取得」で読み、部署名が文字化けするかを確かめる］。経理が UTF-8 で出力できないときは、ストア管理者が CSV を Excel で開き、部署コードの一覧のグリッドに貼り付ける。
- 新しいコードは追加する。廃止されたコードは `Active` を `no` にし、`ValidTo` に日付を入れる。**行は消さない**（過去の付け替えの記録が指しているため）。
- 部署コードの確認を形式だけにするとき（設定 `DeptCodeCheck` を `pattern` にする）は、設定 `DeptCodePattern` の正規表現で確かめる。コードが実在するかは確かめられないので、経理で差し戻されることがある（architecture.md 9.3）。

## 9. id とキーの付け方

| 対象 | 形式 | 例 | 決まり |
|---|---|---|---|
| 成果物の id | `<IdPrefix>-<yyMMdd>-<4 字>` | `s-260929-7k2q` | 英小文字・数字・ハイフンだけ。末尾の 4 字は乱数。列の一意の制約で重複を防ぎ、重複したら振り直す。**変えない・使い回さない**。置き場の行番号は使わない |
| 既存の id | そのまま | `a-0001` | 試作や前の置き場から移したものは変えない |
| 特集の id | `f-<番号>` | `f-5` | ストア管理者が付ける |
| 申し込み ID | `AP-<yyMMdd>-<4 字>` | `AP-260915-7K2Q` | 英大文字・数字。一意 |
| 記録キー（毎月） | `<申し込み ID>-<対象月>` | `AP-260915-7K2Q-2026-09` | 1 つの申し込みにつき、1 か月に 1 行しか作れない |
| 記録キー（買い切り） | `<申し込み ID>-ONCE` | `AP-260920-Q3M8-ONCE` | 1 つの申し込みにつき 1 行しか作れない |
| 記録キー（打ち消し） | `REV-<元の記録キー>` | `REV-AP-260915-7K2Q-2026-09` | 1 つの記録を二度打ち消すことはできない |
| 記録キー（出し直し） | `<元の記録キー>-R<n>` | `AP-260915-7K2Q-2026-09-R1` | 訂正で正しい行を出し直したもの |
| 締め ID | `CLOSE-<計上月度の YYYYMM>` | `CLOSE-202610` | 計上月度 1 つにつき 1 回 |

日付の部分は日本時間で決める（設定 `TimeZone`）。
乱数の 4 字は、フローの式で `guid()` から取る（例: `substring(replace(guid(),'-',''),0,4)`）［要確認: 試験用のフローで式の結果を確かめる］。

## 10. バージョンの上げ方

- 作成者（または保守担当者）が「新しいバージョンを出す」から、新しいバージョン番号とファイルを提出する。画面には、現在のバージョン番号の末尾の数を 1 つ上げた値をあらかじめ入れておく（`2.3` → `2.4`）。
- フローは、新しい番号が現在の番号と異なり、数字とドットだけでできていることを確かめる。`Updated` はその日の日付にする。`PublishedAt` は変えない。
- ファイルは同じ `/<id>/` の中で置き換える。前のファイルはライブラリのバージョン履歴に残る。
- **インディーズ**の成果物は、すぐに新しいバージョンになる。
- **オフィシャル**の成果物は、新しいバージョンの入力内容を審査待ちの更新（7.1）に写して審査を申請し、承認されたらその写しから反映する（既定）。承認されるまで、利用者には承認済みのバージョンが表示される。理由: オフィシャルの成果物は、組織が中身を承認したものである。中身が変われば、承認の前提が変わる。軽微な修正を審査なしにするかどうかは、導入先が決める。
- 金額を変えた場合、すでに承認された申し込みは、申し込んだ時点の金額のまま付け替える（申し込みの `PriceAmount` に写した金額を使う）。

## 11. 削除の扱い

| 対象 | 扱い |
|---|---|
| 成果物 | 消さない。取り下げると `State` を `withdrawn` にする。一覧と検索から外れ、参考にした成果物の系譜には「取り下げ済み」と表示される |
| 成果物のファイル | 消さない。ただし、載せてはいけない情報が入っていたときは、ストア管理者がファイルとそのバージョン履歴を消す。行は残し、理由を操作の記録に書く |
| カテゴリー・部署コード・役割 | 消さない。`Active` を `no` にする |
| 審査の履歴・操作の記録 | 消さない |
| 申し込み | 消さない。状態で表す |
| 付け替えの記録・締めの記録 | **消さない。締めた行は直さない。** 打ち消しの行で直す |
| 受付の行 | 残す。添付は処理が済んだら消す（ファイルは `/<id>/` に移してある） |
| 入手の生の記録 | `RawKeepDays` の日数が過ぎたら消す。部署の名前と月ごとの数だけが集計に残る |

作成者は成果物を削除できない（できるのは取り下げだけ）。

## 12. JSON への書き出しの形式

### 12.1 公開の書き出し（全員が読める）

毎日のフローが `Exports` に置く。形式は試作の `catalog.json` と `categories.json` と同じなので、`build_store.py` でそのまま使える。

```json
{
  "generated": "2026-09-29",
  "note": "（ストア管理者が書くコメント）",
  "features": [ { "id": "f-1", "kind": "story", "tier": "official", "title": "…", "lead": "…", "body": "…", "items": ["a-0003"], "hue": 232 } ],
  "items": [
    {
      "id": "a-0005", "name": "…", "summary": "…", "tier": "official", "kind": "tool", "shelf": "automation",
      "price": { "type": "paid", "amount": 5000, "unit": "1部門あたり月額", "revenue_dept": "D001" },
      "maker": { "name": "…", "org": "…", "id": "（Entra のオブジェクト ID）" },
      "version": "1.4", "updated": "2026-09-10", "published": "2026-06-02",
      "environments": ["…"], "references": [], "files": ["…"],
      "review": { "status": "approved", "by": "審査担当者", "at": "2026-08-15", "note": "…" },
      "signals": ["standard"], "description": "…", "features": ["…"], "tagline": "…"
    }
  ]
}
```

- **追加した項目**は `price.revenue_dept`、`maker.id`、`published`、`state` の 4 つ。どれも無くても試作の画面は動く（画面は知らない項目を読まない）。
- **`review.status` は `none`・`requested`・`approved` の 3 つだけ。** `returned` は書き出さない。
- `review` の中身は状態で決まる。`none` は `{"status":"none"}`、`requested` は `status`・`at`・`note`、`approved` は `status`・`by`・`at`・`note`（試作のデータと同じ）。
- 複数行テキストの列は、改行で分けて配列に戻す。空の行は捨てる。
- `Show` が `no` の特集と、`Active` が `no` の中カテゴリーは書き出さない。
- **取り下げた成果物:** 画面が `state` を扱えるようになるまで（architecture.md 12 章）は、取り下げた成果物を書き出さず、ほかの成果物の `references` からその id を外す。外した id は運営の書き出しに残す。`build_store.py` の検査（参考にした成果物が実在するか）を通すためである。画面が扱えるようになったら、`"state": "withdrawn"` を付けて書き出す。
- `MakerUpn`、`Maintainers`、`ProviderApprovers`、`SourceRequestId` は書き出さない（画面が使わず、公開する理由も無い）。
- `revenue_dept`（部署のコード）を公開の書き出しから外したい組織は、書き出しのフローでこの項目を除く。画面はこの項目を使わない。

### 12.2 運営の書き出し（ストア管理者だけが読める）

月に 1 回、`AdminExports/<YYYY-MM>/` に全件を書き出す。

| ファイル | 内容 |
|---|---|
| `catalog-full.json` | 取り下げた成果物と、公開の書き出しに入れない列も含めた全件 |
| `categories.json` | 公開の書き出しと同じ |
| `reviews.jsonl` | 審査の履歴。1 行 1 件 |
| `applications.jsonl` | 申し込み。1 行 1 件 |
| `charges.jsonl` | 付け替えの記録。1 行 1 件 |
| `closes.jsonl` | 締めの記録。1 行 1 件 |
| `requests.jsonl` | 受付の行（添付は除く） |
| `acq-stats.jsonl` | 入手の集計（人の名前は含まない） |
| `manifest.json` | 各ファイルの件数と、書き出した日時 |

申し込みと付け替えの記録の、1 行ずつの例:

```json
{"id":"AP-260915-7K2Q","item_id":"a-0005","applicant":{"id":"（オブジェクト ID）","dept":"物流（架空）"},"cost_dept":"D007","price":{"amount":5000,"unit":"1部門あたり月額","revenue_dept":"D001"},"billing":"monthly","scope":"dept","state":"active","start_month":"2026-09","end_month":null,"provider_approved_at":"2026-09-15T10:12:00+09:00"}
{"key":"AP-260915-7K2Q-2026-09","kind":"normal","original_key":null,"app_id":"AP-260915-7K2Q","item_id":"a-0005","usage_month":"2026-09","cost_dept":"D007","revenue_dept":"D001","unit_price":5000,"quantity":1,"amount":5000,"state":"closed","close_id":"CLOSE-202610","booking_month":"2026-10"}
```

### 12.3 取り込みと書き出しの往復で一致しない項目

取り込んでから書き出したものを元の `catalog.json` と比べると、違うのは次の項目だけである。これ以外に違いがあれば、取り込みか書き出しの誤りである。
`tools/export_for_sharepoint.py` は、CSV を書き出した後に、この比較を自動で行う。

| 項目 | 違い | 理由 |
|---|---|---|
| `review.status` が `returned` のもの | `none` になる | 利用者の画面では差し戻しを見せない。理由のコメントは審査の履歴に移る |
| `price.revenue_dept` | 有償の成果物に追加される | 付け替えに必要。見本では作成者の部署の架空のコードを入れる |
| `maker.id`・`published`・`state` | 取り込んだ後に追加されることがある | 試作のデータには無い |
| `signals` | 毎日の集計を実行すると、入手の記録から付け直される | 見本の目印は手で付けたもの。見本として見せたい間は、集計のフローを止めておく |
| `generated` | 書き出した日になる | |

### 12.4 取り込み用の CSV（`import/`）

`python3 tools/export_for_sharepoint.py` で、`catalog.json` と `categories.json` から次の CSV を書き出す（BOM 付きの UTF-8。配列は改行でつないで 1 つのセルに入れる）。
会社の PC に Python が無くても使えるように、書き出した CSV をこのフォルダに置いてある。**中身は架空の見本**で、本番のサイトには取り込まない。

| ファイル | 取り込み先 | 行数 |
|---|---|---|
| `import/items.csv` | 成果物 | 34 |
| `import/features.csv` | 特集 | 4 |
| `import/categories.csv` | カテゴリー | 14 |
| `import/review_history.csv` | 審査の履歴（移行した行） | 16 |
| `import/departments.csv` | 部署コードの一覧（架空のコード） | 9 |
| `import/settings.csv` | 設定の既定値 | 25 |

見本の CSV では、次の列は空のままか、列そのものが無い。

- `MakerId`・`MakerUpn`・`PublishedAt`: 試作のデータには無いので、空のまま取り込む。リストの設定で「必須」にしていないので、取り込みは止まらない（3 章の表の下）。見本の `PublishedAt` には、`review.at` があればその日付を、無ければ `updated` の日付を手で入れてよい（「定番」の判定に使う日数の起点になる）。
- `Maintainers`・`ProviderApprovers`・`Reviewer`・`CostApprovers`: ユーザーの列は CSV から取り込めない。試験で必要なときは、画面から入れる。
- `SourceRequestId`・`RequestRowId`・`DecisionRowId`: フローが書く列。`SourceRequestId` に一意の制約を付けたリストで空の行を 2 行作れないときは、1 章のとおり負の数を入れる。

列の名前は `SortOrder`・`ItemVersion` で書く（1 章。`Order`・`Version` という名前では作らない）。

値は元の JSON のまま写す。画面の表記の見直しで `categories.json` の説明文（`tiers[].sub`）や `review.by` の値が変わったら、スクリプトを実行し直す。

## 13. 経理の仕組みへ渡す書き出し

月末の締めのフローが、締めた付け替えの記録を 2 つのファイルに書き出して `AccountingHandoff/` に置く。経理の処理そのもの（仕訳の作成など）は別に作る。ここでは渡すファイルの形式だけを決める。

### 13.1 ファイル

| ファイル | 内容 |
|---|---|
| `charges_<締め ID>.csv` | 締めた付け替えの記録。1 行 1 件 |
| `close_<締め ID>.json` | 締めの見出し。件数と合計金額を入れる |

- 文字コードは UTF-8。先頭の BOM は設定 `CsvBom` で決める（既定は付けない）。経理の仕組みが別の文字コード（例: Shift_JIS）を必要とする場合は、取り込む側で変換する。フローの「ファイルの作成」は UTF-8 で書き込むと記憶している［要確認: T22］。
- 1 行目は見出し行とし、見出しは英字にする（取り込む側の仕組みで扱いやすいため）。日本語の見出しが必要なら、フローの「CSV テーブルの作成」で見出しを変える。
- 行は記録キーの順に並べる。同じ締めを書き出し直しても、同じ内容になる。
- 摘要などの文字列にカンマや改行が入らないよう、フローがそれぞれ全角の読点と空白に置き換える［要確認: 「CSV テーブルの作成」がカンマを含む値を引用符で囲むかを、試験で確かめる］。

### 13.2 CSV の列

| 列 | 内容 | 例 |
|---|---|---|
| `close_id` | 締め ID | `CLOSE-202610` |
| `booking_month` | 計上月度 | `2026-10` |
| `charge_key` | 記録キー（一意） | `AP-260915-7K2Q-2026-09` |
| `kind` | `normal`（通常）か `reversal`（打ち消し） | `normal` |
| `original_key` | 打ち消しと出し直しの行が指す元の記録キー。通常の行では空 | |
| `usage_month` | 対象月 | `2026-09` |
| `cost_dept_code` | 費用を計上する部署のコード | `D007` |
| `cost_dept_name` | その部署の名前（写し） | `物流（架空）` |
| `revenue_dept_code` | 収入を計上する部署のコード | `D001` |
| `revenue_dept_name` | その部署の名前（写し） | `経理企画（架空）` |
| `amount` | 金額（円の整数。打ち消しは負） | `5000` |
| `unit_price` | 単価 | `5000` |
| `quantity` | 数量 | `1` |
| `unit` | 単位 | `1部門あたり月額` |
| `item_id` | 成果物の id | `a-0005` |
| `item_name` | 成果物の名前（写し） | `請求書 PDF の読み取り` |
| `application_id` | 申し込み ID | `AP-260915-7K2Q` |
| `approved_at` | 申し込みが承認された日時（日本時間） | `2026-09-15T10:12:00+09:00` |
| `memo` | 摘要 | `成果物ストア 利用料 a-0005 2026年9月分` |

申し込んだ人の名前やアカウントは入れない（既定）。付け替えは部署と部署の間の処理であり、経理の仕組みに個人の情報を流さないためである。
誰の申し込みかを調べる必要が出たら、ストア管理者が申し込み ID からたどる。個人の情報を入れるかどうかは、導入先が決める。

### 13.3 見出しのファイル

```json
{
  "close_id": "CLOSE-202610",
  "booking_month": "2026-10",
  "closed_through": "2026-09",
  "count": 3,
  "total": 8500,
  "file": "charges_CLOSE-202610.csv",
  "created_at": "2026-10-01T05:07:41+09:00",
  "held": 1
}
```

`count` と `total` は、CSV の行数と `amount` の合計に一致する。経理の仕組みは、取り込む前にこれを照合する。
`held` は、保留にして今回の締めに入れなかった行の数である（行の一覧は締めの記録の `Note` にある）。

### 13.5 経理の仕組みの側に依頼すること

- 締めの完了の通知（締めの記録が `done` になったとき）を受けてから取り込む。締めが途中で止まってやり直すときは、同じ名前のファイルを作り直すためである（architecture.md 6.10 の 8）。
- 取り込む前に、見出しのファイルの `count` と `total` を CSV と照合する。合わなければ取り込まない。
- **同じ締め ID を二度取り込まない。** 取り込んだ締め ID を記録しておく。
- 取り込んだら、ストアに知らせる（画面の「取り込んだ」ボタン、または `close_ack` の受付の行）。この知らせが `AckWaitDays` の日数を過ぎても来なければ、ストア管理者に通知が行く。
- 取り込めない行（部署コードが経理で通らない、など）があれば、記録キーを添えてストア管理者に伝える。ストアは次の締めで打ち消しと出し直しを行う。締めたファイルそのものは作り直さない。
