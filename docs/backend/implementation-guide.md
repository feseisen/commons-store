# 構築の手順

成果物のストアの本線（Microsoft 365 だけで作る方式）を、小さく始めて段階的に広げていく順に作るための手順をまとめる。
構成と判断の理由は [architecture.md](architecture.md)、列と型は [data-model.md](data-model.md) にある。

この文書にある仕様や上限の記述は、学習データから得た記憶にもとづいている。**［要確認］** の箇所は、段階 0 の試験で確かめてから先へ進む。

---

## 誰が何をするか

| 担当 | すること | 必要なもの |
|---|---|---|
| **構築担当者**（業務部門の担当者。この文書の主な読み手） | リスト、Power Apps、Power Automate で構築する。段階 0〜8 と 9a を担当する | 試験用のサイトの所有者であること。既定の環境でアプリとフローを作成できること |
| 開発者 | 本番の画面（SPFx）を作る。段階 9b を担当する | Node.js と TypeScript を扱えること。開発用の PC |
| IT 管理者 | テナントの設定、運用アカウント、アプリカタログを用意する | 下の「IT 管理者への依頼文」を渡す |
| ストア管理者 | ストアを運営する。カテゴリー・特集・役割・設定・部署コードの一覧を更新する。処理が止まったときに対応する | 役割のリストに登録されていること。サイトの所有者であること |
| 経理担当 | 締めた付け替えの記録のファイルを受け取る。部署の一覧を提供する | 下の「経理担当との取り決め」を参照 |
| 利用者（組織の全員） | 成果物を探す・入手する・申し込む・公開する | ブラウザか Teams。操作はすべて画面で完結する |

**進め方の決まり:** 各段階の「確かめ方」をすべて満たしてから、次の段階へ進む。試験は **試験用のサイト** で行い、本番のサイトは段階 9 で作る。見本のデータは架空のものなので、本番には取り込まない。

## 段階 0: 試作を開いて確かめ、導入先の環境を調べる

### やること

1. リポジトリの `store.html` を手元に保存し、ブラウザで開く。SharePoint のライブラリに置いて開こうとしないこと（開かずにダウンロードされる［要確認: T01］）。
2. 次の順に操作し、何がどこに表示されるかを把握しておく。これが、これから作るものの完成形になる。
   - ホーム（特集、区分（オフィシャル・インディーズ）、カテゴリーから探す、最近の更新、定番、人気上昇中）
   - オフィシャルとインディーズのページ → 中カテゴリー → 詳細（`#/item/a-0001`）
   - 検索（「集計」と入力する）
   - 有償の成果物の金額のボタン（「利用の申し込み」のシートが開く）
   - 「公開する」（質問に答えてインディーズに公開する）
   - 左下の名前 → 「審査担当者として表示」をオンにする → 「審査待ち」の画面で承認と差し戻しを試す
   - 「公開した成果物」
3. ブラウザの開発者ツールで、`localStorage` の `store.published`・`store.reviews`・`store.got`・`store.applied`・`store.role` を確認する。**これらが、バックエンドで実際のデータに置き換わる部分である**（architecture.md 12.1）。
4. 下の「導入先で確かめること」（T01〜T25）を 1〜2 日かけて順に試し、結果を記録する（記録の仕方は同じ節の冒頭）。T12 と T17 は、構築したものが無いと試せないため、後の段階で試す。
5. 時間がかかる依頼（運用アカウント、アプリカタログ）は、この時点で IT 管理者に出しておく。

### 必要な権限

- 試作を開くだけなら、権限は要らない。
- 試験には、試験用のサイトの所有者であること、既定の環境でアプリとフローを作成できること、**利用者のアカウント 2 つ**（同僚 2 人に協力してもらってもよい）が必要。

### 確かめ方（すべて満たしたら次の段階へ）

- 「導入先で確かめること」のうち、T12 と T17 以外の結果がすべて埋まっている。T12 は段階 4 と段階 6 の確かめ方で、T17 は段階 8 の確かめ方で埋める。
- 期待どおりにならず代替策を選んだ項目について、どの代替策を選んだかが記録されている。
- 先へ進めなくなる項目（T02・T03・T04 が通らない、など）が残っていない。

## 段階 1: データの置き場を作る

### やること

1. 試験用のサイト（コミュニケーションサイト）を 1 つ作る。
2. **最小構成**のリストとライブラリを作る。対象は、[data-model.md](data-model.md) 2 章の「作る段階」が 1 のもの: 成果物（`Items`）、成果物のファイル（`ItemFiles`）、カテゴリー（`Categories`）、受付（`Requests`）、役割（`Roles`）、設定（`Settings`）、操作の記録（`AuditLog`）。
3. リストの名前は英字で作ってから、表示名を日本語に変える。列も同様に、英字の内部名で作ってから表示名を変える（data-model.md 1 章）。
4. 列の型・一意の制約・インデックスを、data-model.md の表のとおりに設定する。「必須」はリストの設定では付けない。`Title` に既定で付いている必須も外す（data-model.md 1 章と 3 章。必須の項目が入っているかはフローが確認する）。**インデックスはデータを入れる前に付ける。**
5. 成果物のリストとライブラリで、バージョン履歴を有効にする（リストの設定＞バージョン管理の設定）［要確認: T24］。
6. 権限を設定する（architecture.md 7.2）。
   - サイトの閲覧者に組織の全員を入れる。
   - サイトに SharePoint のグループを 2 つ作る（ストアの審査担当者、ストアの経理担当）。ストア管理者はサイトの所有者のグループに入れる。リストとライブラリの権限は、個人ではなくグループに与える。
   - 権限レベルを 2 つ作る（サイトの設定＞サイトのアクセス許可＞アクセス許可レベル）［要確認: 作れるか］。「投稿（削除なし）」は、「投稿」をコピーして「アイテムの削除」を外したもの。「追加と閲覧だけ」は、アイテムの追加・アイテムの表示・アイテムを開く・ページの表示・開く・ユーザー情報の参照・リモート インターフェイスの使用だけを持つもの（アイテムの編集と削除を外す）。
   - 受付: リスト単位で権限の継承を切る。継承を切ると、所有者・メンバー・閲覧者のグループがそのまま引き継がれる。メンバーのグループ（既定の権限は「編集」）は「リストの管理」を持ち、アイテムレベルのアクセス許可の設定そのものを変更できるので、引き継がれたメンバーと閲覧者のグループは外す。残すのは、所有者のグループと、全員に与える「投稿（削除なし）」だけにする［要確認: リストの設定＞詳細設定の「アイテムレベルのアクセス許可」の注記に、どの権限を持つ人が全部の行を読めるかが書いてある。「編集」の内容もアクセス許可レベルの画面で確かめる］。詳細設定の「アイテムレベルのアクセス許可」で、読み取りと編集をどちらも「自分が作成したアイテムのみ」にする。「検索結果に表示する」を「いいえ」にする［要確認: リストの設定＞詳細設定にこの項目があるか。T08 の SharePoint の検索で表示されないことを確かめる］。
   - 操作の記録: 権限の継承を切り、所有者のグループ（ストア管理者と運用アカウント）だけにする。
7. 設定のリストに `import/settings.csv` の内容を入れる。役割のリストに、自分をストア管理者として登録する。
8. 運用アカウントをサイトの所有者に加える（まだ用意できていなければ、当面はストア管理者 2 人で代わりに進める）。

### 必要な権限

- 試験用のサイトの所有者（利用者がサイトを作れない設定の組織では、SharePoint 管理者に作成を依頼する）。

### 確かめ方（すべて満たしたら次の段階へ）

- 利用者 A が受付に 1 行作っても、利用者 B からは、リストの画面でも「Excel にエクスポート」でもその行が見えない（T08 の一部）。
- 利用者 A は成果物のリストに書き込めない（「新しいアイテム」のボタンが表示されず、REST で書き込むと拒否される）。試し方は下の「REST での試し方」を参照。
- 成果物のリストにインデックスが 8 つ付いている。`ItemId` に一意の制約が付いている。

## 段階 2: 試作のデータを取り込む

### やること

**取り込みの方法は 2 つある。** どちらか一方でよい。

**(a) CSV で入れる（Python は不要）**

`docs/backend/import/` の CSV を使う（`tools/export_for_sharepoint.py` が書き出したもの。文字コードは BOM 付きの UTF-8 で、配列は改行でつないで 1 つのセルに入れてある）。

| ファイル | 取り込み先 |
|---|---|
| `items.csv` | 成果物 |
| `features.csv` | 特集（段階 3 で作る。先に作ってもよい） |
| `categories.csv` | カテゴリー |
| `review_history.csv` | 審査の履歴（段階 5 で作る） |
| `departments.csv` | 部署コードの一覧（段階 4 で作る。架空のコード） |
| `settings.csv` | 設定 |

- 段階 1 で作ったリストの「グリッドで編集」に、Excel で開いた CSV の範囲をコピーして貼り付ける［要確認: T21］。Microsoft Lists の「CSV から新しいリスト」は使わない（別のリストが新しくでき、段階 1 で設定したインデックス・一意の制約・権限・バージョン履歴が付かないため）。
- 改行を含むセル（`Features`・`Environments` など）の中身が改行ごとに 1 行ずつ保たれるかを、先に 1 行だけ入れて確かめる（T21）。保たれなければ (b) の方法に切り替える。

**(b) JSON を読むフローで入れる**

1. 書き出しのライブラリ（`Exports`）を作り、`import/` フォルダーに `catalog.json` と `categories.json` を置く。
2. 手動で実行するフローを 1 本作る。
   - 「ファイル コンテンツの取得」で `catalog.json` を読む → 「JSON の解析」で解析する（または `json()` の式でそのまま読む）［要確認: ファイルの内容が文字列で返るか、エンコードされて返るかを試す］。
   - `items` の 1 件ごとに、成果物のリストに 1 行作る。配列は改行でつなぐ（`join(item()?['features'], decodeUriComponent('%0A'))`）［要確認: 試験用のフローで 1 件だけ流し、列の中で改行されているかを確かめる］。`price` は 3 つの列に分ける。有償なら、`RevenueDeptCode` に作成者の部署のコード（`departments.csv` の `DeptName` と `maker.org` を突き合わせて求める）を入れる。`version` は `ItemVersion` に入れる。`review.status` が `returned` なら `none` にし、差し戻しの理由は審査の履歴に入れる。`signals` はそのまま入れる。
   - `features` の 1 件ごとに、特集のリストに 1 行作る。
   - `categories.json` の内容をカテゴリーのリストに入れる（対応は data-model.md 5 章）。中カテゴリーの色相には `categories.csv` の `Hue` を使う。
3. どちらの方法でも、**本番のサイトには取り込まない**（見本は架空のデータのため）。

**続けて、書き出しのフローを作る（architecture.md 6.15）。**

1. 手動で実行する（あとで毎日の定時実行にする）フローで、成果物・特集・カテゴリーを読み、`catalog.json` と `categories.json` の形式に組み替えて `Exports` に置く（data-model.md 12.1 の決まり）。
2. `store-template.html` を `Exports` に置く。その中の 2 つの差し込み位置（`/*__CATALOG__*/` と `/*__CATEGORIES__*/`）を JSON で置き換え、`</` を `<\/` に置き換えたものを、`store.html` として置く。

### 必要な権限

- 試験用のサイトの所有者であること。Power Automate でフローを作成できること。

### 確かめ方（すべて満たしたら次の段階へ）

- 書き出した `catalog.json` を元の `catalog.json` と比べ、違いが data-model.md 12.3 の例外だけである（`a-0105` の `returned` が `none` になる、有償の 4 件に `revenue_dept` が加わる、など）。キーの順序は問わない。
- 書き出した `store.html` を保存して開くと、試作と同じ 34 件が同じ見た目で表示される。
- 書き出した JSON を `build_store.py` のあるフォルダーに置き、`python3 build_store.py` を実行すると、検査に通る（任意。実行できる人がいる場合）。

## 段階 3: 閲覧用の画面（Power Apps）

### やること

0. 特集（`Features`）のリストを作り（data-model.md 4 章）、`import/features.csv` を入れる（試験用のサイトだけ）。
1. キャンバスアプリを 1 つ作り、成果物・カテゴリー・特集・役割・設定のリストをデータソースとして接続する。
2. 画面を作る。試作の画面を横に開いて見比べながら、同じ流れと文言にそろえる。
   - ホーム: 特集、区分（オフィシャル・インディーズ）、カテゴリーから探す、最近の更新、定番、人気上昇中
   - オフィシャルとインディーズのページ
   - 中カテゴリーの一覧（無償・有償と対応環境で絞り込む。並べ替えは「更新日順」と「名前順」）
   - 詳細（パンくず、アイコン、名前、サブタイトル、作成者、主ボタン、インディーズの説明ボックス、情報の帯、説明、ストアによる確認、作成者からの情報（対応環境、特徴、有償なら費用の付け替えと収入の計上部署、バージョン）、参考にした成果物、これを参考にした成果物）
   - 検索（対象は名前・サブタイトル・概要・作成者・部署・対応環境・中カテゴリーの名前）
   - 作成者のページ（**`MakerId` で絞り込む**。名前では絞り込まない）
   - 特集のページ
3. 起動時に、公開中の成果物をまとめて読み込む（例: `ClearCollect(colItems, Filter(Items, State.Value = "listed"))`［要確認: 選択肢の列の等号比較を委任できるか］）。読み込み中は、その旨を 1 行表示する。
4. アプリの設定＞全般＞データ行の上限を 2,000 にする［要確認: T16］。
5. 詳細へのリンク: アプリの URL に `?item=<id>` を付けて開けるようにする（`Param("item")`）［要確認: 試験用のアプリを `?item=a-0005` を付けて開き、詳細が表示されるかを確かめる（段階 3 の確かめ方）］。この URL の形式を設定 `DetailLinkFormat` に入れる。
6. 見た目: `docs/design/spec.md` 2 章のトークン（色、文字サイズの段階、角丸）を、アプリの名前付き数式か変数に移す。アイコンは、中カテゴリーの色相と記号から作った SVG を画像として表示する（`"data:image/svg+xml;utf8," & EncodeUrl(...)`）［要確認: 試験用のアプリで 1 つだけ表示し、ブラウザと Teams のタブで見えるかを確かめる］。
7. SharePoint のページ（Power Apps の Web パーツ）と Teams のタブに埋め込む［要確認: T19］。

### 必要な権限

- 既定の環境でアプリを作成できること。試験に協力する利用者にアプリを共有できること。

### 確かめ方（すべて満たしたら次の段階へ）

- 試験に協力する利用者 3〜5 人が、説明を受けずに目当ての成果物の詳細までたどり着ける。
- オフィシャルとインディーズの区別が、どの画面でも分かる。
- `a-0105`（差し戻された見本）が、どの画面でも差し戻しとして表示されない。
- どの一覧も、既定の並び順は更新日の新しい順になっている。目印や数値で並べ替える式が無い。星の評価も点数も無い。
- `?item=a-0005` を付けて開くと、その成果物の詳細が表示される。
- 作成者のページが `MakerId` で絞り込まれる（見本は `MakerId` が空なので、試験として 2 件だけに同じ値を入れて確かめる）。

## 段階 4: 公開

### やること

0. 部署コードの一覧（`Depts`）と有償のファイル（`PaidFiles`）は、この段階で作る（data-model.md 3.1・7.6）。部署コードの一覧は全員が読めるようにし、`import/departments.csv`（架空のコード）を入れる（試験用のサイトだけ）。有償のファイルはライブラリ単位で権限の継承を切り、引き継がれたメンバーと閲覧者のグループを外して、所有者のグループと審査担当者のグループ（読み取りのみ）だけにする。
1. 運用アカウントで、受付の処理のフロー（トリガーは Power Apps (V2)、入力は受付の行の番号）を作る。分岐は `publish`・`update`・`withdraw`・`maintainers`（architecture.md 6.1・6.2）。
   - 最初に「項目の取得」で行を読む。**フローを呼び出した人と行の登録者が同じ人かを、オブジェクト ID で比べる**。呼び出した人は、トリガーの出力のヘッダー `x-ms-user-email` から取る（式 `triggerOutputs()?['headers']?['x-ms-user-email']`）［要確認: T05］。登録者は、`Author` の `Claims`（`i:0#.f|membership|<UPN>` の形式）から取る。両方を Office 365 ユーザーの「ユーザー プロフィールの取得 (V2)」で検索し、返ってきた `id` どうしを比べる（この操作はメールアドレスでも検索できると記憶している［要確認: T05］）。メールアドレスの欄どうしは比べない（UPN とメールアドレスが異なる組織があるため）。一致しないときは、呼び出した人が役割のリストの `store_admin`（`Active`＝`yes`）であれば処理を続け、登録者を身元として使い、処理し直した人を操作の記録に書く（「処理し直す」のための経路）。それ以外なら `rejected` を返して終える（architecture.md 5.3）。
   - 行の値は、ここで読んだ時点のものだけを使う。後から書き換えられた値は使わない（受付の行は、作った人が編集できるため）。
   - `ProcessState` が `new` でなければ、行に記録済みの結果を返すだけで終える。
   - 入力の確認（architecture.md 6.1 の 6）→ id の採番（data-model.md 9 章）→ 成果物のリストに 1 行作成 → 添付を `/<id>/` に移動 → 受付の行に結果を書き戻す → 操作の記録 → 「PowerApp またはフローに応答する」（`result`・`itemid`・`note`）→ 通知。
   - 最後に「失敗したら」の分岐を置き、行を `failed` にしてストア管理者に通知する。
2. 監視のフロー（15 分ごと）を作る。作成から 10 分を過ぎても `new` のままの行を、ストア管理者に通知する（architecture.md 6.16）。
3. 画面を作る。
   - 公開の質問: 受付のリストに接続したフォーム（EditForm）で作ると、添付ファイルをそのまま扱える［要確認: 試験用のフォームで添付を 1 つ付けて送信し、受付の行に添付が付くかを確かめる］。質問は試作と同じ 7 つ。**有償を選んだら、金額・単位（設定 `PriceUnits`）・収入の計上部署（部署コードの一覧から選ぶ。既定では自分の部署のコードに限る。architecture.md 6.1 の 6）・申し込みを承認する人（任意。収入の計上部署の人に限る）の欄を表示する。**
   - 最後の確認の 1 行: 「会社の外に出せない情報や個人の情報を含みません」（チェックしないと送信できない）。
   - 送信ボタンは、一度押したら押せないようにする。フォームを開いたときに `ClientToken` に `GUID()` を入れる。
   - 送信が完了したら（`OnSuccess`）、フローを呼び出す（例: `Set(varRes, 受付の処理.Run(frmPublish.LastSubmit.ID))`）。結果が `published` なら詳細へ移り、「インディーズに公開しました」（審査を申請したときは「公開し、審査を申請しました」）と表示する。`rejected` なら理由を表示する。
   - 「公開した成果物」: 自分の成果物（`MakerId` が自分のもの）と、自分の受付の行の状態を表示する。
   - 作成者の数字の行: 公開したときと「公開した成果物」を開いたときに、自分の行が無ければ 1 行作る（この手順は段階 8 で追加する。段階 4 では作らない）。
   - ストア管理の画面: 未処理の行の一覧と「処理し直す」（ストア管理者にだけ表示する。フローの側でも役割のリストで確かめる）。
4. 運用アカウントを、アプリとフローの共同所有者にする。ストア管理者 2 人も共同所有者にする。

### 必要な権限

- 運用アカウントの接続（SharePoint、Office 365 ユーザー、Microsoft Teams、Office 365 Outlook）。
- アプリからフローを呼び出せること（T05）。

### 確かめ方（すべて満たしたら次の段階へ）

- 公開してから数秒〜十数秒で詳細に移り、別のアカウントで見たインディーズの一覧にも表示される。
- 別のアカウントからは、ほかの人の受付の行が、画面・リストの画面・REST・添付の URL・検索・Excel への書き出しのどれからも見えない（T08）。
- 送信ボタンを素早く 2 回押しても、成果物は 1 件しかできない。
- ほかの人の行の番号を渡してフローを呼び出すと `rejected` になる（Power Apps の画面にテスト用のボタンを一時的に置いて試し、試した後は削除する）。
- 有償なのに収入の計上部署が無い公開は `rejected` になる。収入の計上部署にほかの部署のコードを選ぶと、その部署に承認の依頼が届き、承認されるまで公開されない。
- 10 MB・30 MB・100 MB のファイルで公開を試し、どの大きさで失敗するかを記録する（T12 の前半）。
- 作成者でない人による `update` と `withdraw` は `rejected` になる。取り下げた成果物は一覧と検索から消え、それを参考にした成果物の側では「取り下げ済み」と表示される。
- 操作の記録に、公開・更新・取り下げの行が残る。

## 段階 5: 審査

### やること

1. 審査の履歴（`ReviewLog`）を作り、審査担当者とストア管理者だけが読めるようにする（所有者のグループと審査担当者のグループ）。`import/review_history.csv` を入れる（試験用のサイトだけ）。審査待ちの更新（`PendingUpdates`）と審査待ちのファイル（`PendingFiles`）も作り、同じく審査担当者とストア管理者だけが読めるようにする（書き込むのは運用アカウント。data-model.md 7.1）。
2. 受付の処理のフローに `review_request` と `review_decision` の分岐を追加する（architecture.md 6.3〜6.5）。`update` の分岐には、オフィシャルの成果物を更新するときの処理（質問への回答とファイルを審査待ちの置き場に写す。architecture.md 6.2 の 4）を追加する。
3. 画面を作る。
   - 詳細と「公開した成果物」に「審査を申請する」を置く（差し戻されたものは「再申請する」）。
   - 「審査待ち」の画面（役割のリストに `reviewer` として登録されている人にだけ表示する）: 申請の古い順の一覧（申請からの日数を表示する）、選んだ 1 件の詳細、操作の帯（コメントの入力欄、「差し戻す」「承認する」）。コメントが空なら「差し戻す」を押せない。帯に「承認のコメントは詳細に公開されます。差し戻しのコメントは作成者にだけ届きます」と表示する。
   - 「審査の履歴」の表（`ReviewLog` から読む）。
4. 毎日の監視に、`ReviewWaitDays` を過ぎた申請の期限切れの処理と、役割のリストとグループの食い違いの検出（architecture.md 6.16）を追加する。
5. 見本のうち申請中の 2 件（`a-0102`・`a-0115`）には、承認の記録が無い。ストア管理者が代わりに `review_request` を出し直すか、そのまま「審査待ち」の画面で判定する。

### 必要な権限

- ストア管理者が役割のリストとグループを編集できること。試験用の審査担当者を 1 人決め、役割のリストとストアの審査担当者のグループの両方に登録する。

### 確かめ方（すべて満たしたら次の段階へ）

- 役割のリストに無い人が作った `review_decision` の行は `rejected` になる（リストの画面から直接作った行はフローを呼び出さないので `new` のまま残る。ストア管理の画面の「処理し直す」でその行を処理してから結果を確かめる）。
- 作成者は自分の成果物を承認できない（自分を審査担当者にして試す）。
- 承認すると、id・`PublishedAt`・参考にした成果物が変わらないまま、オフィシャルに移る。詳細に承認日とコメントが表示される。
- 差し戻すと、その理由は作成者の「公開した成果物」と通知にだけ表示される。別のアカウントでは、画面・リスト・REST のどこにも理由が表示されない。
- コメントが空の差し戻しは、画面ではボタンを押せず、リストから直接作った行もフローが拒否する（リストの画面から直接作った行はフローを呼び出さないので `new` のまま残る。ストア管理の画面の「処理し直す」でその行を処理してから結果を確かめる）。
- オフィシャルの成果物の新しいバージョンを出すと、承認されるまで、利用者には前のバージョンと前回の審査日が表示される。審査担当者は、審査待ちの内容とファイルを開ける。差し戻すと成果物は変わらない。承認すると新しいバージョンに切り替わる。
- 2 人が同じ成果物をほぼ同時に判定すると、後から判定したほうが `rejected`（すでに判定済み）になる。

## 段階 6: 入手と申し込み

### やること

**入手**

1. 入手の記録（`Acquisitions`）を作る。受付と同じく権限の継承を切って引き継がれたグループを外し、「自分の行だけ」にして、検索結果に表示しない。全員に与えるのは「追加と閲覧だけ」（行を作れるが編集できない。architecture.md 7.2）。
2. 詳細と一覧の「入手」では、自分の行が無ければ 1 行書き込み、ファイルをダウンロードさせる（例: `If(IsBlank(LookUp(Acquisitions, ItemId = varItem.ItemId)), Patch(Acquisitions, Defaults(Acquisitions), {Title: varItem.ItemId, ItemId: varItem.ItemId, ItemVersion: varItem.ItemVersion})); Download(<ファイルの URL>)`）［要確認: Download で SharePoint のファイルがダウンロードされるか］。
3. ボタンの文言は、自分の入手の記録をもとに決める（「入手」→「入手済み」。ツールは「開く」）。
4. 「入手できない場合」のシートには、`/<id>/` の置き場所と作成者への連絡方法を表示する（区分を含むパスは表示しない）。

**申し込み**

1. 申し込み（`Applications`）を作る。入手の記録と同じく「自分の行だけ」にし、全員に「追加と閲覧だけ」を与え、検索結果に表示しない（有償のファイルと部署コードの一覧は段階 4 で作成済み）。
2. 本番では、部署コードの一覧を経理から受け取る（段階 7 の部署の取り込みと、下の「経理担当との取り決め」を参照）。
3. 申し込みの処理のフロー（トリガーは Power Apps (V2)）を作る（architecture.md 6.7・6.8）。
   - 入力の確認 → 申し込み ID の採番 → 金額と単位を成果物から写す → 「受け付けました」と応答 → 費用側の承認（設定 `CostApproval` に従う）→ 提供側の承認（承認のコネクタを使う。選択肢は「承認」「断る」。期限は費用側と合わせて `ApplyWaitDays`。architecture.md 6.8 の 3）→ 回答が返ったら、申し込みと成果物を読み直す（取りやめや取り下げの後なら何も変えない）→ 承認なら状態を変え、有償のファイルをメールで届ける。
   - 読み込むのは、最終更新者が運用アカウントになっている行だけにする（利用者が作ったままの行は信用しない。data-model.md 7.3）。
   - 付け替えの記録はまだ作らない（段階 7 で追加する）。
4. 画面を作る。
   - 金額のボタン → 「利用の申し込み」のシート: 金額、単位、作成者、提供部署（成果物の「収入の計上部署」）、申込者、**費用の計上部署**（コードでも名前でも検索できる候補から選ぶ。初期値は、名簿上の自分の部署と一覧の `DirectoryDept` が一致するコード）、コメント（任意）。説明文は「提供部署が承認すると、選んだ部署の費用として自動で付け替えます（月末締め・翌月度計上）。経理の手続きは不要です。」（継続の場合は「解約するまで毎月付け替えます」を加える）と「申し込むと、名前と部署が提供側に届きます」。
   - 「申し込む」を押すと申し込みの行を書き込み（`Title` と `ClientToken` に同じ乱数を入れる）、フローを呼び出す。ボタンの表示は「申し込み中」になる。
   - **自分の申し込み**（新しい画面）: 申し込みの一覧、状態、単位と金額、「解約する」「費用の部署を変える」「取りやめる」（結果が出る前だけ）。
   - ボタンの文言は、自分の申し込みの状態をもとに決める（architecture.md 12.2 の 6）。
5. 受付の処理のフローに `subscription_end`・`cost_dept_change`・`application_cancel` の分岐を追加する（architecture.md 6.12）。
6. 毎日の監視に、利用中の申し込みの保留（部署コードの廃止、アカウントの無効化、成果物の取り下げによるもの）と、承認待ちのまま残っている申し込みの検出を追加する（architecture.md 6.16）。

### 必要な権限

- 承認のコネクタが使えること（T10・T11）。運用アカウントからメールを送信できること。
- ストア管理者が部署コードの一覧を編集できること。

### 確かめ方（すべて満たしたら次の段階へ）

- 入手した成果物が、別の端末でも「入手済み」と表示される。ほかの人の入手の行は、どの経路からも見えない（T08）。
- 申し込むと、提供側の承認者の Teams に承認の依頼が届く。承認するとファイルがメールで届き、状態が「利用中」（買い切りは「済み」）になる。
- 断ると、その理由が申し込んだ人に届き、ボタンの表示が金額に戻る。
- `ApplyWaitDays` を 1 にして待つと期限切れになり、両者に通知が届く。
- 費用の計上部署に自分の部署以外のコードを入れると、費用側の承認の依頼が先に届く。
- 同じ部署の 2 人目が「1部門あたり月額」の同じ成果物に申し込むと、承認を経ずに「加わった」になり、ファイルが届く。
- 自分の成果物への申し込みや、一覧に無いコード・廃止したコードでの申し込みは `rejected` になる。
- 画面を改ざんして違う金額を送っても、申し込みの `PriceAmount` は成果物に設定された金額になる（リストの画面から直接作った行はフローを呼び出さないので未処理のまま残る。ストア管理の画面の「処理し直す」でその行を処理してから結果を確かめる）。
- 利用者がリストの画面から自分の申し込みの `State`・`CostDeptCode`・`PriceAmount` を編集しようとすると、拒否される。入手の記録も編集できない。
- リストの画面から `State`＝`active` の申し込みの行を直接作っても、付け替えにも締めにも使われず、監視のフローが未処理の行として通知する。
- 買い切りを済ませた人が同じ成果物にもう一度申し込むと `duplicate` になる。
- 10 MB・30 MB・100 MB のファイルで、申し込み後のファイルの受け渡し（メール）がどの大きさで失敗するかを記録する（T12 の後半）。

## 段階 7: 付け替えと月末の締め

### やること

1. 付け替えの記録（`Charges`）、締めの記録（`Closes`）、経理への引き渡し（`AccountingHandoff`）を作る。読めるのはストア管理者と経理担当だけにする（権限の継承を切り、所有者のグループと、経理担当のグループに読み取りの権限を与える。architecture.md 7.2）。記録キー（`Title`）と、締めの記録の `BookingMonth` に一意の制約を付ける。
2. 申し込みの処理のフローで、「承認」の後に付け替えの記録を 1 行作る手順を追加する（architecture.md 6.9）。対象月は、提供側が承認した日時を日本時間に換算して決める。費用の計上部署と収入の計上部署が同じなら作らない。
3. 月末の締めのフローを作る（architecture.md 6.10）。
   - トリガーは毎日早朝の定時実行。先月分が締め済みなら何もしない。
   - **手動で起動する経路も作り、入力で「締める月」を指定できるようにする。** 試験用のサイトで、月末を待たずに締めを試すためである。本番ではストア管理者だけが実行できるようにする。1 本のフローに置けるトリガーは 1 つだけなので、締めの手順を子フローにする（トリガーは「手動でフローをトリガーします」、入力は締める月、最後に「PowerApp またはフローに応答する」）。親フローは 2 本作る。定時実行の親フローと、ストア管理の画面から呼び出す親フロー（Power Apps (V2)）である。どちらも「子フローを実行する」で子フローを呼び出す［要確認: 既定の環境の Power Automate で「ソリューション」を開き、新しいソリューションを作れるか。その中にフローを作れるか。子フローの接続は「この接続を使う」（運用アカウント）にする］。ソリューションが使えないときは、次の方法をとる。ストア管理の画面から、受付に `close_run` の行（`TargetId`＝締める月）を書き込む。毎日定時に動く締めのフローがその行を見つけたら、同じ手順でその月を締める（反映は翌朝になる）。
   - 「複数の項目の取得」には、どれも上位の件数と改ページを設定する（architecture.md 5.5）。
   - CSV は組み込みの「CSV テーブルの作成」で作り、「ファイルの作成」で保存する［要確認: T22］。BOM が必要なら先頭に付ける（`concat(decodeUriComponent('%EF%BB%BF'), body('CSV_テーブルの作成'))`）［要確認: T22 の試験で、BOM を付けた CSV を Excel で開き、文字化けしないかを確かめる］。
4. 受付の処理のフローに `correction` と `close_ack` の分岐を追加する（architecture.md 6.11・6.10 の 10）。
5. 画面を作る。
   - ストア管理者向け: 付け替えの記録の一覧（対象月・状態で絞り込む）、「取り消す」「訂正する」、締めの記録の一覧、保留の一覧。
   - 経理担当向け: 締めの記録の一覧と「取り込んだ」。
6. 毎日の監視に、`running` のまま残った締めと、経理の取り込み待ちの検出を追加する。
7. 経理担当と、引き渡しの形式を取り決める（下の「経理担当との取り決め」）。
8. 部署の取り込みのライブラリ（`DeptImport`）を作る。権限の継承を切り、引き継がれたメンバーと閲覧者のグループを外して、所有者のグループと、「投稿（削除なし）」を与えた経理担当のグループだけにする。経理への引き渡しのライブラリとは分ける（経理担当が引き渡しのファイルを書き換えられないようにするため）。
9. 部署コードの取り込みのフロー（手動で実行する）を作る。部署の取り込みのライブラリにある最新の CSV（列: コード、名前、有効期間の開始日、終了日。UTF-8）を読み、部署コードの一覧の `Title` と突き合わせる。一覧に無いコードは追加する。名前や期間が変わったコードは更新する。CSV から消えたコードは `Active`＝`no`、`ValidTo`＝今日の日付にする。行は削除しない。終わったら、追加した数・更新した数・無効にした数をストア管理者に通知する（data-model.md 7.6）。

### 必要な権限

- 役割のリストと、ストアの経理担当のグループに経理担当を登録する。ライブラリとリストに権限を設定する。

### 確かめ方（すべて満たしたら次の段階へ）

試験用のサイトで、手動の起動を使って 3 か月分の締めを進める。

1. 承認すると、付け替えの記録がちょうど 1 行できる。フローの実行を「再送信」しても 2 行目はできない（作る前に既存の行を探すため。探索をすり抜けても一意の制約で止まる）。
2. 継続の申し込みで 3 か月分締めると、付け替えの記録が月ごとに 1 行ずつできる。解約した月の翌月からはできない。
3. 同じ月を 2 回締めても、2 回目は何も起きない。
4. CSV の行数と金額の合計が、見出しのファイルの `count` と `total` に一致する。行は記録キーの順に並ぶ。付け替えの無い月でも、見出し行だけのファイルができる。
5. 締めた行を訂正すると、元の行は変わらず、次の締めに打ち消しの行（負の金額）と再計上の行が入る。
6. 月末の 23 時台に承認した申し込みの対象月が、その月になる（T25）。
7. 締めの前に部署コードを廃止すると、その行は保留になってファイルに入らず、ストア管理者に通知が届く。
8. 経理担当が「取り込んだ」を押すと、締めの記録に日時が入る。押さないまま `AckWaitDays` を過ぎると通知が届く。
9. 費用の計上部署と収入の計上部署が同じ申し込みでは、付け替えの記録ができない。
10. 経理システムの担当者が、[data-model.md](data-model.md) 13.4 の見本のファイルを取り込めることを確かめている（システムがまだ無ければ、形式の合意だけでよい）。
11. 継続の申し込みを承認した月の翌月 1 日に締めても、処理が止まらない。承認した月の記録は 1 行のままである。
12. 利用中の継続の申し込みを 120 件作って締めると、付け替えの記録が 120 行でき、CSV にも 120 行入る（architecture.md 5.5）。
13. 締めのフローを途中で取り消し、「運営の手順」の「フローが止まったとき」の 5 の手順で締め直すと、CSV に全部の行が 1 回ずつ入り、見出しのファイルの件数と合計が一致する。
14. 締めを 1 か月止めてから再開すると、抜けた月の分も月ごとに締められる（締めの記録が 2 行、ファイルが 2 組できる）。
15. 保留（`held`）の行を訂正で `open` に戻すと、次の締めの対象になる。
16. 経理担当が部署の取り込みのライブラリに CSV を置き、ストア管理者が取り込みのフローを実行すると、追加したコードと廃止したコードが一覧に正しく反映される。経理担当は、部署の取り込みのライブラリ以外には書き込めない。

## 段階 8: 目印と作成者だけの数字

### やること

1. 入手の日ごとの数（`AcqDaily`）、入手の集計（`AcqStats`）、作成者の数字（`MakerNumbers`）を作る。前の 2 つはストア管理者だけが読めるようにする。作成者の数字は「自分の行だけ」にし（全員に「追加と閲覧だけ」を与える）、検索結果に表示しない。
2. 毎日の集計のフローを作る（architecture.md 6.13）。最後に書き出しのフロー（段階 2）を呼び出す形にして、毎日の定時の処理としてまとめる。
3. 公開したときと「公開した成果物」を開いたときに、自分の作成者の数字の行が無ければ 1 行作る（`Title`＝`maker`）。「公開した成果物」の各行に、作成者の数字（入手している部署の数、参考にされた件数、利用中の申し込みの数）を表示する。
4. 見本の目印（`signals`）は手作業で付けたもので、最初の集計で外れる。見本として見せておきたい間は、集計のフローを止めておく。

### 必要な権限

- これまでの権限で足りる。

### 確かめ方（すべて満たしたら次の段階へ）

- 試験用の設定で閾値を下げ（例: `RisingMin30` を 2 にする）、試験用のアカウントで入手すると、翌日に「人気上昇中」が付く。閾値を戻すと外れる。
- 作成者自身と保守担当者による入手は、数に含まれない。
- 同じ日の集計を 2 回実行しても、数が変わらない。
- 同じ人が同じ成果物の入手の行をリストの画面から毎日追加しても、数は 1 回分しか増えない。
- 作成者の数字が作成者にだけ見える（T08 のすべての経路で確かめる）。
- 目印の付いた成果物が区分の 2 割を超えると通知が届く。集計を止めると、`StaleAlertHours` が過ぎた後に通知が届く。
- 1 週間運用した後、1 日の要求数が上限の 1 割以下に収まっている（T17）。

### REST での試し方（段階 1 の確かめ方、T08、T09）

業務担当者が REST で試すときの手順。どれもブラウザだけで試せる。

**読む（T08）:** ブラウザのアドレス欄に次の URL を入力して開く。

```
https://〈テナント〉.sharepoint.com/sites/〈サイトの URL の名前〉/_api/web/GetList('/sites/〈サイトの URL の名前〉/Lists/Requests')/items
```

- リストは、英字のまま残る URL（`/Lists/Requests`）で指定する。表示名を日本語に変えた後は、表示名で探す `getbytitle('Requests')` では見つからない［要確認: 表示名を変えた試験用のリストで、両方の形式の URL を開いて比べる］。

// 段階 1: 成果物のリストに書けないこと。403 なら期待どおり
console.log((await post(list('Items') + '/items', { Title: 'REST の試し' })).status);

const r1 = await post(list('Requests') + '/AddValidateUpdateItemUsingPath', {

## 経理担当との取り決め

経理の処理（仕訳の作成など）は、経理の側で別に用意する。ストアの側で決めたことと、経理の側にお願いすることを 1 枚にまとめて渡す。

> 件名: 成果物の利用料の部署間付け替えに関するデータの受け渡しについて
>
> 社内の成果物のストアでは、有償の成果物の利用料を部署間で付け替えます。利用者も作成者も、経理の操作は行いません。申し込みが承認されると付け替えの記録が自動で作られ、月末に締めて翌月度に計上する形でファイルをお渡しします。
>
> **お渡しするもの**
> - 毎月 1 日の早朝に、先月分を締めたファイル 2 つをライブラリ〔　〕に置きます。`charges_CLOSE-<計上月度>.csv`（1 行に 1 件）と `close_CLOSE-<計上月度>.json`（件数と合計）です。
> - 列の定義は〔添付: data-model.md 13.2〕のとおりです。金額は円単位の整数で、打ち消しは負の数で表します。付け替えが無い月も、見出し行だけのファイルを置きます。
> - 締めたファイルは作り直しません。誤りは、翌月のファイルに打ち消しの行と正しい行を入れて訂正します。
>
> **お願いしたいこと**
> 1. 部署コードの一覧を CSV でお送りください（コード、名前、有効期間）。変更があったときも、その都度お送りください。置き場所は〔部署の取り込みのライブラリ〕です。文字コードは UTF-8 でお願いします（Shift_JIS だと、取り込むときに部署名が文字化けします）。
> 2. 取り込む前に、見出しのファイルの件数と合計を CSV と照合してください。
> 3. 同じ締め ID のファイルを二度取り込まないようにしてください。
> 4. 取り込みが済んだら、ストアの画面で「取り込んだ」を押してください（または、経理システムの側から知らせる方法をご相談させてください）。
> 5. 取り込めない行があれば、記録キーを添えて〔ストア管理者〕にお知らせください。
>
> **ご確認いただきたいこと**
> - 文字コード（UTF-8 でよいか、BOM が必要か）と、見出し行の項目名（英字でよいか）。
> - 税の扱いが必要か。
> - 申し込んだ人の情報（名前やアカウント）が必要か。現在は入れていません。
> - 計上月度の考え方（先月分を今月度に計上する）で問題ないか。

## 運営の手順（ストア管理者）

**中カテゴリーを追加する:** カテゴリーのリストに 1 行追加する（`Type`＝`shelf`、`CatId`＝英小文字の id、`Title`、`Parent`＝大カテゴリーの id、`SortOrder`、`Hue`、`Active`＝`yes`）。新しい中カテゴリーにはアイコンの記号が必要なので、画面の側（Power Apps の記号の一覧、SPFx の雛形の `sym-<id>`）にも追加する。id は後から変えない。

**中カテゴリーを廃止する:** `Active` を `no` にする。その中カテゴリーに成果物が残っていれば、書き出しのフローが通知する。行は削除しない。

**特集を変更する:** 特集のリストを直接編集する。`Items` には成果物の id を 1 行に 1 つずつ書く。表示したくなければ `Show` を `no` にする。

**役割を入れ替える:** 役割のリストで元の担当者の `Active` を `no` にして、新しい担当者を追加する。**SharePoint のグループでも同じように、元の担当者を外して新しい担当者を加える**（審査担当者はストアの審査担当者のグループ、経理担当はストアの経理担当のグループ、ストア管理者はサイトの所有者のグループ）。役割のリストの行は削除しない。毎日の監視のフローが役割のリストとグループのメンバーを比べ、食い違いがあればストア管理者に通知する［要確認: グループのメンバーの一覧は、SharePoint のコネクタの「SharePoint に HTTP 要求を送信します」（標準のコネクタと記憶している）で `/_api/web/sitegroups/getbyname('<グループ名>')/users` を読んで取得する。フローの編集画面で、この操作にプレミアムのラベルが付いていないかを確かめる］。

**部署コードを取り込む:** 経理担当が部署の取り込みのライブラリ（`DeptImport`）に置いた CSV を、取り込みのフローを手動で実行して取り込む。無くなったコードは `Active` が `no` になる。利用中の申し込みが廃止されたコードを使っていれば、翌朝の監視のフローがその申し込みを保留にして通知する。

**付け替えを取り消す・訂正する:** 付け替えの記録の画面で「取り消す」か「訂正する」を使う。締め済みの行そのものは変わらず、次の締めに打ち消しの行と再計上の行が入る（architecture.md 6.11）。

**毎朝確認するもの:** 毎日の集計の完了通知（届いていなければ集計が止まっている）、未処理の行の通知、保留の通知。月初めは、締めの通知と経理の取り込み状況も確認する。

**フローが止まったとき:**
1. Power Automate の「マイ フロー」で、運用アカウントのフローの実行履歴を開く。
2. 失敗した実行で、赤い印の付いた操作を開いて原因を確認する。
3. 接続が切れていれば（「接続」の画面に警告が表示される）、運用アカウントでサインインし直す。
4. 受付の行が `new` や `failed` のまま残っていれば、ストア管理の画面の「処理し直す」で処理する。
5. 締めが `running` のまま残っていれば、フローの実行履歴で、その実行が止まっている（実行中でない）ことを確かめる。付け替えの記録の締め ID を見て、どこまで進んだかも確かめる。確かめたら、締めの記録の `State` を `failed` に変え、手動の起動で同じ月を締め直す（architecture.md 6.10 の 2）。締め ID が付いた行が再び拾われることはないが、ファイルは締め ID の付いたすべての行から作り直すので、前回の分も含まれる。締めの完了通知が出るまでは取り込まないよう、経理に伝える。

**年に数回の見直し:** 役割のリスト（異動した人がいないか）と SharePoint のグループ。フローとアプリの共同所有者。運用アカウントの接続。手動で実行するだけのフローが無効にされていないか（Power Automate の一覧で「オフ」になっていないか。architecture.md 7.3）。設定の閾値と、目印の付いた成果物の割合。入手の生の記録を保持する日数。

**担当者が替わるとき:** 運用アカウントのサインイン情報を引き継ぐ（組織の決まりに従う）。共同所有者と役割のリストの登録を入れ替え、この「運営の手順」を引き渡す。
