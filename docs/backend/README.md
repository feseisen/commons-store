# バックエンドの設計

試作（`store-template.html` と `catalog.json`）は、ブラウザの中だけで完結している。公開・審査・入手・申し込みの結果はそのブラウザにしか残らず、ログインの仕組みも無い。
このフォルダでは、それを **組織で共有する本番のデータと権限** に置き換える設計を、**勧める方式 1 つと、ほかの方式 2 つ** の形で説明する。

- **Microsoft 365 方式（勧める方式）: Microsoft 365 だけで作る。** サーバーを持てず、バージョン管理の基盤も無い組織を前提にする。
- **Git 方式: Git の基盤がある場合。** 成果物を Git に置き、公開と昇格をプルリクエストで進める。
- **サーバー方式: サーバーを持てる場合。** 小さな Web アプリとデータベースを置き、画面は試作をほぼそのまま使う。

有償の成果物は **部署間の付け替え** として扱う。申し込みが承認されると付け替えの記録が作られ、月末に締めて、翌月に計上するために経理システムへ渡す。経理システムそのものは、この設計の範囲外である。

このスクリプトは、CSV を作ったあと、CSV から `catalog.json` を組み立て直して元のファイルと突き合わせ、あらかじめ決めてある例外以外の違いがあれば知らせる。`departments.csv` の部署コード（`D001` など）は架空のもので、導入先の部署コードに置き換える。

## 3 つの方式の比較

| | **Microsoft 365 方式（勧める方式）** | Git 方式 | サーバー方式 |
|---|---|---|---|
| **必要なもの** | SharePoint のサイト 1 つ、Power Apps と Power Automate（標準のコネクタだけ）、運用アカウント 1 つ。本番の画面（SPFx）を作るには、Node.js と TypeScript を扱える開発者 | GitHub Enterprise Cloud か Azure DevOps Services と、全員分のアカウント。CI と社内向けの Pages。**有償の分には Microsoft 365 方式の仕組みも必要** | Azure のサブスクリプション（または社内のサーバー 1 台）、Entra ID のアプリ登録、データベース、ファイルの置き場所、Web アプリを保守する担当者 |
| **管理者の作業** | 少ない。サイトの作成、環境とデータ損失防止のポリシーの確認、運用アカウントの作成。本番の SPFx だけは、アプリカタログへの配置と承認が必要で、数週間かかることがある | 中程度。Git の基盤の契約とライセンス数（シート）、シングルサインオン、GitHub App の登録、ルールセット、Pages の許可 | 多い。サブスクリプションとリソース グループ、アプリの登録と同意、アプリ ロールの割り当て、予算のアラート、メール送信の権限 |
| **ライセンス** | 利用者の Microsoft 365 に含まれる、Power Apps と Power Automate の標準の利用権の範囲に収める。プレミアムのコネクタ（HTTP、Dataverse、カスタムコネクタ）は使わない［要確認: T04］ | 閲覧するだけの人にもライセンス（シート）が必要になる見込み［要確認: 販売窓口］ | 利用者に追加のライセンスは要らない見込み。Azure の従量課金の費用がかかる（最小構成で月に数千円〜1 万円ほど）［要確認: Azure の料金計算ツール］ |
| **試作との見た目の近さ** | 当面作る Power Apps 版は作り直しになり、構成は同じで見た目は近い。本番の SPFx 版は試作とほぼ同じ［要確認: T20］ | 試作と同じ（CI が同じ 1 枚の HTML を生成する）。公開の途中だけ、Git の基盤の画面に移る | 試作と同じ（試作の HTML に、サーバーとの接続部分を足す） |
| **向いている組織** | サーバーを持てず、バージョン管理の基盤も無い。作るのは業務部門の担当者 | 全員が Git の基盤のアカウントを持ち、変更の履歴をプルリクエストで残したい | Azure か社内のサーバーを用意でき、保守する人がいる。即時の反映や、閲覧者ごとの細かい表示の出し分けが必要 |
| **有償（付け替え）** | リストとフローで、申し込み・承認・付け替えの記録・月末の締め・経理への引き渡しを行う | Git には置けない（全員に見えてしまう）。**Microsoft 365 方式の仕組みをそのまま使う** | データベースのテーブルに同じ形で持ち、経理へは同じ形式のファイルで渡す |

**Microsoft 365 方式を勧める理由**（詳しくは architecture.md 1 章）: サーバーを持てず、バージョン管理の基盤も無いという前提の下で動くのは、この方式だけである。書き込みの操作を「受付のリストに 1 行書く → フローが確かめて反映する」という 1 つの流れにそろえるので、画面を替えてもフローはそのまま使える。データの形は `catalog.json` と同じ 1 件 1 レコードのままなので、前提が変わったらほかの方式へ移行できる（architecture.md 20 章）。

## 用語

| 言葉 | 意味 |
|---|---|
| 委任 | Power Apps が、絞り込みの処理を SharePoint の側に任せること。委任できない式では、先頭の数百〜2,000 件だけを手元に取得してから絞り込むので、それより後ろの行が、気づかないうちに欠ける［要確認: T16］ |
| REST | SharePoint のリストを、画面を通さずに URL（`/_api/...`）で直接読み書きする方法。権限のテストは、画面だけでなくこの方法でも行う（implementation-guide.md の「REST での試し方」） |
| 一意の制約 | 列の設定「一意の値を適用する」。同じ値の行を 2 つ作れなくする。二重登録を防ぐために使う |
| インデックス | 列の設定「インデックス付きの列」。件数が増えても、その列での絞り込みがエラーにならないようにする設定 |
| BOM | ファイルの先頭に付ける 3 バイトのマーク。Excel などが、文字コードが UTF-8 であることを見分けるのに使う |
| テナント | 組織の Microsoft 365 全体の契約と設定のまとまり。IT 管理者が管理する |
| JSON Lines | 1 行に 1 件の JSON を並べたファイル（拡張子 `.jsonl`）。記録を追記していく用途に向く |
| SPFx・Web パーツ・アプリカタログ | SharePoint のページに部品（Web パーツ）を追加するための開発の仕組みが SPFx。作った部品を組織に配布するための置き場所がアプリカタログで、置くには SharePoint 管理者の承認が必要 |
| 運用アカウント | 特定の人ではなく、役割のために用意するユーザー アカウント（いわゆるサービス アカウント）。フローと接続の所有者にして、担当者の異動でフローが止まらないようにする |
| アクセス許可レベル | SharePoint で、実行できる操作をまとめたもの（閲覧、投稿、編集など）。この設計では「投稿（削除なし）」と「追加と閲覧だけ」をサイトに作る（architecture.md 7.2） |

## ［要確認］について

このフォルダの文書に書いた製品の仕様・上限・ライセンスの扱い・管理画面の場所は、**Claude の学習済みの知識に基づくもの** で、執筆の時点では製品の最新のドキュメントと照合していない。製品の仕様は変わることがあり、組織の設定によっても異なる。

- そうした箇所には **［要確認］** を付け、確認の方法か確認する相手を添えてある。
- **［要確認: T01］** のように番号が付いているものは、[implementation-guide.md の「導入先で確かめること」](implementation-guide.md#導入先で確かめること) に確認の手順がある。確認は段階 0 で行い、各段階の「完了の条件」を確かめるときにも行う。
- 確認した結果が記載と異なっていたら、先にこのフォルダの文書を直してから作る。違いが設計に影響する場合（例: 標準の範囲に収まらない、自分の行だけを読める設定が効かない）にとる代わりの方法は、architecture.md の 16 章（リスクと対策）に書いてある。

［要確認］の無い箇所は、この設計の中で決めたこと（データの形、流れ、既定の値とその理由）である。
