# 成果物のストア — 要件

依頼者の言葉から決まったこと（R）と、こちらで決めた既定（D。依頼者から別の指示があるまで有効）を分けて書く。
書き始めたのは 2026-09-28。画面の見た目と構成は [`design/spec.md`](design/spec.md)、バックエンドの作り方は [`backend/README.md`](backend/README.md) を正本とする。

## 1. 何のために

組織の中では、さまざまな部署がそれぞれツールや素材を作っているが、発表する場がばらばらである。そこで、**ツールも素材も含めた成果物を公開する場を一つにまとめる**。
前身は「作った人の手柄が残る形で資産を共有する」社内コモンズ（インナーソースの基盤）であり、目的は前身から変わらず、**作った人がきちんと評価されること**である。

利用者から見て「App Store のようなものだ」と分かる使用体験を目指す。目指すのは App Store・Google Play・Steam の**仕様をなぞることではなく、体験が近いこと**である。

## 2. 依頼者の言葉から決まったこと

| # | 要件 | 依頼者の言葉（要旨） |
|---|---|---|
| R1 | **区分が 2 つ**: オフィシャル（審査済み）とインディーズ（審査なし）。最初の入り口から分かれている | 「審査済みのコンテンツと未審査のコンテンツ、それぞれで明確に分類されてほしい。入り口が変わるみたいなこと」 |
| R2 | **インディーズは審査なしですぐに公開できる**。玉石混交でよい | 「いちいち審査を通すとか、そういうまどろっこしいことをやらずに、とにかくスピーディーにできるというのが利点」 |
| R3 | **オフィシャルは、組織が「皆さん使ってよい」と認めたもの** | 「当社の公式のサービスとある意味認める」 |
| R4 | **どちらの区分にも大カテゴリーと中カテゴリーがある**。大カテゴリーの例は「ツール」と「素材」 | 「ツールという大カテゴリーがあって、中カテゴリーとして、例えば……」「その他の大カテゴリーとして素材がある」 |
| R5 | **無償が既定。有償も選べる** | 「無償でも当然と提供していいんだけど、有償という選択肢も取れますよ」 |
| R6 | **レビュー（星・低評価）は付けない** | 「レビューは別にいらない」「低評価つくのもあれなので」 |
| R7 | 素材の例: **デザイン仕様書のカタログ**（HTML のデザインをマークダウンで記述したもの） | 「素材という意味で、かなり近い」 |
| R8 | 足りない情報は、**要件整理として依頼者に質問しながら**進める | 「要件定義として僕に質問をしながら進めてください」 |
| R9 | **有償とは部署間の付け替えのこと**（2026-09-29）。利用者は申し込むときに**費用を計上する部署のコード**を入力し、作成者は公開（リリース）のときに**収入を計上する部署のコード**を登録しておく。**経理の処理を利用者にはさせない**。承認されると裏側で自動的に処理され、**月末締め・翌月度計上**とする。経理処理そのものは別途作る | 「実際の経理処理は別途実装する必要がある。少なくとも、経理処理をユーザーに行わせるつもりはありません。（承認されたら自動で経理処理が裏側で動くようにする。月末締め・翌月度計上の予定）」「ユーザー側では費用として計上する部署のコードを入力し、作成者側はリリース時に収入として計上する部署のコードを登録しておく、というイメージ」 |

前身の社内コモンズから引き継ぐ要件:

- **作成者を順位で並べない。人気の情報は、探す人のためだけに使う**（「定番」などの目印）
- **利用者は専門家ではない。操作は画面の中で完結させる**
- **サーバーを立てられないことを前提とする**。Microsoft 365（SharePoint・Power Apps・Power Automate）で作るのが本命で、共有フォルダに置く静的なページは試作と予備の位置づけ
- **帰属を残す**。公開するときに参考にした成果物を追加し、系譜として記録する

## 3. こちらで決めた既定（依頼者から別の指示があるまで）

| # | 既定 | 理由 |
|---|---|---|
| D1 | 前身の社内コモンズの設計（SharePoint＋Power Apps が本命、共有フォルダ版が試作）の**上に積み上げる**。作り直さない | 手戻りを避けるため。「探す→詳細→入手／公開」という画面の流れが、そのままストアの骨組みになる |
| D2 | ~~有償は「金額と区分を持てて、表示できる」まで~~ **［2026-09-29 の R9 で置き換え］**申し込みの承認・付け替えの記録・月末の締め・経理への引き渡しまでを作る（`backend/architecture.md` 9 章）。お金そのものは動かさず、経理処理は別途作る | 依頼者が、有償の意味を「部署間の付け替え」と決めたため |
| D3 | **オフィシャルとインディーズは同じカテゴリーの階層を使う** | 探す人が区分を切り替えても迷わないようにするため。一方の区分にしか成果物の無いカテゴリーは、もう一方では空のまま表示しない |
| D4 | **インディーズからオフィシャルへの昇格がある**。審査担当者が承認するとオフィシャルに移り、インディーズでの履歴（公開日、参考にした成果物）は引き継ぐ | 「審査済み」は状態であり、別の成果物ではないため。同じ成果物を 2 回登録させない |
| D5 | **審査担当者は役割（ロール）として定義し、誰をその役割に就けるかは導入する組織が決める** | 組織が判断すべき事柄であるため |
| D6 | **大カテゴリーは「ツール」「素材」の 2 つから始め、後から増やせるようにする**。中カテゴリーは、導入する組織が名前を決められる一覧として持つ（`categories.json`） | 中カテゴリーを、こちらで固定しないため |
| D7 | **数字は探す人のためだけに**使う。「人気上昇中」「定番」の目印は表示する。成果物ごとの数字は、その作成者にだけ見せる | 作成者どうしを競わせないため |
| D8 | **ストアの一覧はカタログのデータ（1 件 1 レコード）から作る**。データの形式は置き場所（共有フォルダ／SharePoint／GitHub）によらない | 使うツールや契約が変わっても、データと画面を移行できるようにするため |
| D9 | **申し込みを承認するのは提供する側**（成果物の承認者。未設定なら作成者）。自分の部署以外のコードに付け替えるときだけ、費用を負担する側の承認も挟む。月額のものは、解約するまで毎月の締めで 1 か月分ずつ付け替えの記録を作り、日割りはしない | R9 は「承認されたら」とだけ述べており、誰が承認するかは決まっていない。収入を受け取る側が提供を約束する立場にあるので、既定ではそちらを承認者とする（`backend/architecture.md` 9.2） |

## 4. 用語

| 言葉 | 意味 | 画面での呼び方 |
|---|---|---|
| オフィシャル | 審査を通り、組織が「皆さん使ってよい」と認めた成果物 | オフィシャル（審査済み） |
| インディーズ | だれでも審査なしで公開できる成果物。玉石混交 | インディーズ（審査なし） |
| （オフィシャル／インディーズの別） | 成果物がどちらに属するか | 区分 |
| 大カテゴリー | 成果物の種類。まずは「ツール」「素材」 | 「ツール」「素材」の名前で呼ぶ（総称は画面に出さない） |
| 中カテゴリー | 大カテゴリーの中の分類（例: ツール＞表計算、素材＞デザイン仕様書） | カテゴリー |
| 無償／有償 | 利用に対価が必要かどうか。有償は金額と単位（1人あたり月額・1部門あたり月額・1人分の買い切り）を持つ | 無償／有償（金額） |
| （有償の費用の扱い） | 部署間の付け替え（R9） | 費用の付け替え。利用者の側は「費用の計上部署」、作成者の側は「収入の計上部署」。申し込んだ後は「申し込み中／提供部署の承認待ち」 |
| 作成者 | 成果物を公開した人。組織のアカウントで確認する | 作成者 |
| 参考にした成果物 | 公開するときに登録する、利用させてもらった成果物（帰属） | 参考にした成果物（逆向きは「参考にされた件数」） |
| （審査する役割） | オフィシャルへ移すかどうかを決める人 | 審査担当者（その画面とナビは「審査待ち」） |
| （審査の手続き） | オフィシャルへ移すまでのやりとり | 申請する／承認する／差し戻す／再申請する。状態は 審査済み／未審査・申請中 |
| （使える環境・バージョン・入手の動き） | 詳細ページの情報の帯に出す欄 | 対応環境／バージョン／入手の傾向（値は「定番」「人気上昇中」） |
| （成果物の特徴の箇条） | 作成者が公開するときに書く、短い句の箇条書き（`features`） | 特徴 |

画面の文言はこの表の右の列に合わせる（2026-09-29、依頼者の「日本語が非常に不自然」を受けて直した）。

## 5. 利用者から見た体験

1. **開くと、まず区分を選ぶ入り口がある**: オフィシャル／インディーズ。いまどちらの区分にいるかは、画面に常に表示される。切り替えは 1 回の操作で済む
2. **区分の中は、大カテゴリー→中カテゴリーの順に分かれる**。App Store の「Today／ゲーム／App」と同じ深さ。カテゴリーごとに数件を横並びで出し、「すべて見る」で一覧を開く
3. **1 件のカードで分かること**: 名前、サブタイトル、カテゴリー、作成者と部署、無償／有償（金額）、対応環境、目印（定番など）。**星や点数は表示しない**
4. **詳細**: 説明、バージョン、更新日、対応環境、参考にした成果物（系譜）、ファイル。**「入手」はボタン 1 つ**（ダウンロード）。有償の場合は金額と単位が表示され、申し込むときに費用の計上部署を選ぶ（R9）
5. **公開**: 名前と説明・カテゴリー・無償／有償（有償なら金額・単位・収入の計上部署）・対応環境・参考にした成果物・ファイルを入力する。**入力を終えるとすぐにインディーズに並ぶ**。オフィシャルにしたい場合は、「審査を申請」をオンにすると審査担当者に申請が届く
6. **審査**: 申請された順に一覧で表示する。「承認する」でオフィシャルへ移し、「差し戻す」では理由を 1 行書いて作成者に返す。履歴が残る
7. **探す**: 名前・説明・カテゴリー・作成者で検索できる。区分をまたいで探せる（検索結果には区分の印が付く）
8. **公開した成果物**: 区分ごとの一覧、審査の状態、作成者にだけ見える数字を表示する

## 6. データの形式（置き場所によらない）

1 件を 1 レコードとする。共有フォルダでは `catalog.json` に記録し、SharePoint ではリストの列に対応させる（列の対応は `backend/data-model.md`）。

| 項目 | 型 | 例 |
|---|---|---|
| `id` | 文字列（変えない） | `a-0001` |
| `name` | 文字列 | 月次集計の計算表 |
| `tagline` | 文字列（20 字まで） | 月次の締めを、貼るだけで |
| `summary` | 文字列（60 字まで） | 売上の一覧を貼るだけで、部門別・月別の集計とグラフを作成します |
| `description` | 文字列 | |
| `features` | 文字列の配列（特徴。画面の見出しも「特徴」） | |
| `tier` | `official` / `indie` | `indie` |
| `kind` | 大カテゴリーの id | `tool` |
| `shelf` | 中カテゴリーの id | `spreadsheet` |
| `price` | `{ "type": "free" }` または `{ "type": "paid", "amount": 数, "unit": 文字列, "revenue_dept": 部署コード }`（`revenue_dept` は収入を計上する部署。R9） | `{ "type": "paid", "amount": 3000, "unit": "1部門あたり月額", "revenue_dept": "D003" }` |
| `maker` | `{ "name", "org" }` | |
| `version` / `updated` | 文字列 / 日付 | |
| `environments` | 文字列の配列（対応環境） | `["Excel 2016以降", "ブラウザ"]` |
| `references` | id の配列（参考にした成果物） | |
| `files` | 相対パスの配列 | |
| `review` | `{ "status": "none"/"requested"/"approved"/"returned", "by", "at", "note" }` | |
| `signals` | 探す人のための目印（`standard`＝定番、`rising`＝人気上昇中） | 集計に基づいて自動で付ける。手では書かない |

区分・カテゴリーの階層・目印は、別ファイルの `categories.json` に持ち、名前は導入する組織が決められる。同じファイルの `departments` が部署コードの一覧で（試作では架空の `D001`〜`D009`）、申し込みの「費用の計上部署」と公開の「収入の計上部署」の選択肢になる。本番では、経理側の部署の一覧から取り込む（`backend/data-model.md` 7.6）。

## 7. やらないこと

- 星・点数・レビューの本文・低評価
- 作成者のランキング、貢献度の一覧
- 決済（お金を動かすこと）と、経理処理そのもの。付け替えの記録を経理の仕組みへ渡すところまでを作る（R9）
- 利用した人の名前を作成者以外に見せること（見せるかどうかは組織が判断する）

| 2 | 組織の中の「有償」は何を指すか | 表示だけ／部署間の付け替え／実際の支払い | 金額の単位、申し込みの流れ |
|   | **［済み 2026-09-29］答えは「部署間の付け替え」（R9）** | | |
| 3 | オフィシャルを認めるのは誰か | ★役割として定義し、導入する組織が決める／特定の窓口の部署／各部署の長 | 審査画面の作り |

## 9. 画面の設計

画面の見た目と構成は、このファイルではなく **[`design/spec.md`](design/spec.md)** を正本とする。そこに至るまでの調査と設計案の比較は、[`design/README.md`](design/README.md) からたどれる。**調査は生成 AI（Claude）の学習データ（記憶）に基づいており、実物のページは読んでいない。**数値は実物と異なる可能性があるので、実物の App Store を開いて見比べられる人が確かめるのがよい。

要件のうち画面に反映したもの: R1（区分が 2 つ）→ ホームの区分のタイルと、2 つの区分それぞれのページ。R2（インディーズは審査なしですぐに公開）→ 公開のフォームの入力を終えるとすぐに並び、末尾のトグルで審査を申請できる。R3（オフィシャル＝組織が認めたもの）→ 詳細の「ストアによる確認」の 1 行目。R4（大→中カテゴリー）→ 大カテゴリー→カテゴリーの順の構成と、カテゴリーのタイル 8 つ。R5（無償が既定で、有償も選べる）→ ボタンに金額、詳細に単位。R6（レビューなし）→ 星も点数も無く、目印は「定番」「人気上昇中」の 2 つだけ。R9（部署間の付け替え）→ 申し込みのシートの「費用の計上部署」、公開の「収入の計上部署」、詳細の情報表の「費用の付け替え」。
